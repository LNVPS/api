# API Changelog

All notable changes to the LNVPS APIs are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Security

- **Admin job-feedback WebSocket was not authenticated** — `GET /api/admin/v1/jobs/feedback` accepted a `?auth=` NIP-98 event but only *parsed* it: `Event::from_json` verifies neither the signature nor the event id, so any caller could hand-craft an unsigned JSON event carrying an arbitrary `pubkey` and stream the internal worker job bus (provisioning detail for every VM on the platform). The signature is now verified and bound to the endpoint path, and the connection additionally requires `virtual_machines::view` — it previously required no permission at all.

- **Unauthenticated request could crash the API process** — a payment-provider webhook (`/api/v1/webhook/{stripe,revolut,bitvora}`) carrying a header value with a non-UTF-8 byte panicked the handler. With `panic = "abort"` on the release profile that took down the whole process, so a single `curl` was a total outage, repeatable indefinitely. Header values are now decoded lossily. Separately, the webhook body was buffered into memory unbounded (taking the raw `Request` bypasses axum's `DefaultBodyLimit`); it is now capped at 256 KB.

- **Authenticated request could crash the API process** — `GET /api/v1/vm/{id}/renew` and `GET /api/v1/subscriptions/{id}/renew` accepted an unbounded `intervals`, which overflowed the projected-expiry arithmetic; `chrono` panics rather than saturating, so `?intervals=1000000000` aborted the process. `intervals` is now rejected outside `1..=120` with a 400, and every expiry calculation saturates. The `max_prepay_days` horizon check was no defence here — it ran *after* the panic point.

- **API processes no longer abort on a handler panic** — `panic = "abort"` has been removed from the release profile and both the public and admin routers are wrapped in a panic guard, so a future panic reachable from request data degrades to a 500 on that one request instead of an outage. Two further panic sites reachable from ordinary requests were also fixed (a NaN comparison in host/disk capacity sorting, and a malformed stored CIDR).

- **NIP-98 auth events are now single-use, shorter-lived, and bound to this host and to the request body** — an auth event was previously replayable for its whole ten-minute window, its `u` tag was compared only by *path* (so an event a user was tricked into signing for a hostile origin via NIP-07 replayed successfully here), and the `payload` tag was never checked (so a captured auth for a bodied request could be reused with a different body). The window is now 60 seconds, each event id may be used once, and a `payload` tag — when the client sends one — must match the SHA-256 of the actual body. Clients that do not send `payload` are unaffected; clients that do now get their body cryptographically bound. **Clients must not reuse a signed auth event across requests — and must make sure each event is actually distinct.** A nostr event id is the hash of (pubkey, created_at, kind, tags, content) and `created_at` has only one-second resolution, so two *identical* requests (same key, URL and method) signed within the same second produce the same event id, and the second is rejected as a replay with `Auth check failed: Credential has already been used`. Clients that may issue the same request twice in quick succession (retries, double-clicks, parallel fetches) should include a random `nonce` tag in the auth event; unknown tags are ignored by the server.

- **Role *definition* no longer allows privilege escalation** — role *assignment* was already guarded, but `POST /api/admin/v1/roles` and `PATCH /api/admin/v1/roles/{id}` placed no constraint on the permissions a role could be given. Because an admin may hold the role they are editing, anyone with `roles::update` could add every permission in the system to their own role without the assignment guard ever running. Both endpoints now refuse to define a role holding permissions the caller does not themselves hold (super admins are unrestricted). Permission sets are also validated up front, so an invalid entry can no longer leave a half-populated role behind.

- **Admin API gains the protections the public API already had** — the admin API previously ran with no rate limiting and none of the security headers. It now carries the same per-IP limiter, panic guard, CORS and `nosniff`/`DENY`/`no-referrer`/CSP headers.

- **Rate limiting can no longer be bypassed by omitting forwarding headers** — a request with neither `X-Forwarded-For` nor `X-Real-IP` skipped the limiter entirely, because the server was not supplying a peer-address fallback. Both binaries now do, and a request with no resolvable address is billed to a shared bucket rather than waved through. The unauthenticated LNURL-pay endpoints (`/.well-known/lnurlp/{id}` and `/api/v1/vm/{id}/renew-lnurlp`) have also moved into the strict bucket.

- **Session (Bearer) tokens can now be revoked** — a session JWT was valid for its full 30-day life with no way to invalidate it. Tokens now carry the account's `session_version`, which is checked on every request; the new `DELETE /api/v1/account/sessions` bumps it, logging the account out everywhere. This matters most for admins, whose Bearer token carries admin rights.

- **WebAuthn challenge tokens are single-use** — the ceremony state lived entirely in the signed token with nothing marking it spent, so a captured `POST /api/v1/webauthn/login/finish` body could be replayed within the 5-minute TTL to mint further sessions. The authenticator signature counter was no defence (most passkeys report a constant 0).

- **Email verification links now expire after 24 hours** — a link had no expiry, so one sitting in an old or compromised inbox stayed usable forever.

- **WhatsApp verification sends are capped per account** — 5 per hour per user, in addition to the existing per-IP limit. Each send costs money and delivers a message to a caller-chosen number, and the per-IP bucket alone did not stop an attacker spreading across addresses.

- **The free-form LIR agreement renderer now requires authentication** — `GET /api/v1/legal/sponsoring-lir-agreement` rendered an official-looking contract entirely from caller-supplied data with no auth, making it a phishing primitive on the LNVPS origin. (It was never XSS: the template escapes its values and the CSP blocks script.)

- **The OAuth `localhost` redirect exemption is off by default** — any `localhost` post-login redirect was permitted in every environment. It is now gated behind the new `allow-localhost-redirect` OAuth setting, which must be enabled explicitly for local development.

- **Role assignment no longer allows privilege escalation** — `POST /api/admin/v1/users/{id}/roles` and `DELETE /api/admin/v1/users/{id}/roles/{role_id}` previously required only `users::update` and placed no constraint on which role was granted, so any admin who could edit users (e.g. the built-in `user_manager` role) could grant themselves `super_admin` and gain every permission in the system. Both endpoints now require `roles::update` instead, refuse self-assignment, require `super_admin` to grant or revoke `super_admin`, and refuse to grant a role whose permissions are not a subset of the caller's own. The self-revoke lockout guard now only applies to the **last** super admin, so an unwanted `super_admin` grant can be handed back instead of being permanent. By default only `super_admin` holds `roles::update`, so role assignment is now a super-admin-only operation unless a custom role grants it.

- **Per-client-IP rate limiting on the public API** — all consumer endpoints now sit behind an in-process fixed-window limiter (600 req/min per IP general; 10 req/min per IP on brute-force-sensitive auth and verification endpoints: OAuth login/callback, WebAuthn register/login, email verification, WhatsApp verify/confirm, and the contact form). Exceeding a limit returns `429 Too Many Requests` with a `Retry-After` header. Clients with well-behaved retry/backoff behaviour are unaffected.

- **WhatsApp verification codes are now invalidated after 10 failed confirmations** — the 6-digit code previously had unlimited online guesses. After 10 wrong attempts the pending code is cleared and a fresh one must be requested (`POST /api/v1/account/whatsapp/verify`).

- **Verification secrets are stored as SHA-256 hashes, not plaintext** — `users.email_verify_token` and `users.whatsapp_verify_code` now hold only the hash of the value sent to the user, so a read-only database leak no longer exposes live verification links/codes. **Any email or WhatsApp verification pending at deploy time is invalidated** by the accompanying migration; affected users simply re-request verification.

- **VM upgrades must now strictly increase at least one resource** — `POST /api/v1/vm/{id}/upgrade` and the upgrade quote endpoint previously accepted any in-plan spec, including one smaller than the current VM, producing a zero/negative prorated charge that applied a reduced VM. Requests that shrink CPU, memory or disk (or change nothing) now fail with an error. Downgrades remain available by reinstalling a smaller template.

- **Client-IP geolocation now trusts the right-most `X-Forwarded-For` entry** — the left-most entry is client-controllable when an edge proxy appends rather than replaces, which let a caller spoof the IP used as EU VAT place-of-supply evidence.

- **Security headers on all API responses** — `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and a restrictive `Content-Security-Policy` are now set on every response (previously the HTML invoice/verification/agreement pages had none).

- **Billing-detail mismatch warnings no longer name the mismatched fields** — `PATCH /api/v1/account` with a VAT number returns a generic "some billing details do not match the VAT registration" warning instead of listing which of name/street/postcode/city differed, closing an oracle that could probe third parties' EU VAT registration data. The warning is still surfaced (valid numbers still validate; mismatches are still non-fatal).

- **Contact form hardens email header values** — `POST /api/v1/contact` strips control characters from the sender name and subject (and caps the subject) before placing them in outgoing mail headers.

### Fixed

- **Deleting a VM now stops its billing** — a soft-deleted VM (the path every paid VM takes) kept its subscription `is_active` with auto-renewal on, so the customer went on being invoiced for a machine that no longer exists and `GET /api/admin/v1/subscriptions` still listed it as active. Deleting a VM now deactivates its subscription and clears auto-renewal, the same rule the admin app-deployment delete already applied. Purging a VM was unaffected: it removes the subscription outright.

- **Placement reconciliation no longer skips disabled hosts and pools** (issue #391) — `enabled` is a scheduling flag ("place no new VMs here"), but reconciliation used the same filtered host/disk listings, so a disabled host was never polled and a disabled pool could never be named. Draining a pool starts by disabling it, which is exactly when disks and VMs move, so every hand-run `qm move-disk`/`qm migrate` performed during a drain went unrecorded: `disk_id` kept charging capacity to a pool that no longer held the data, and a VM on a disabled host kept a stale `host_id`, which every lifecycle operation is aimed at. Reconciliation now observes every host and pool regardless of `enabled` (including hosts in a disabled region), while VM placement and capacity accounting keep using the filtered listings — a disabled target is reconciled *into*, never *scheduled onto*. A disabled host that cannot be reached also no longer counts as unreachable, so a host taken out of service does not hold up reconciliation of the hosts that did answer.

- **Admin VM endpoints work again after a host is disabled** — `GET /api/admin/v1/vms` and `GET /api/admin/v1/vms/{id}` resolved each VM's host through the provisioning host listing, which returns only *enabled* hosts in *enabled* regions. Disabling a host therefore broke the entire admin VM list with `VM {id} references non-existent host {host_id}` — precisely when an operator most needs to see those VMs. Both endpoints now resolve hosts and regions regardless of their enabled state.

- **Discount codes are matched case-insensitively** — code lookup was `WHERE code = ?`, so whether a customer typing `save10` matched the published `SAVE10` depended on the `discount.code` column's collation, i.e. on the server default in force when the table was created. Codes are now normalised to upper case: the admin API upper-cases a code when it is created or updated, and the pricing engine upper-cases what the customer typed before looking it up. The unique index still does the duplicate check, and `SAVE10`/`save10` can no longer be two campaigns. Codes are displayed in upper case, whatever case the admin typed.

- **An unusable discount code now returns 400 instead of 500** — applying a code that does not exist (or is expired, inactive, another company's, or usage-limited) at checkout returned HTTP 500 `{"error":"An internal error occurred"}`, so the customer saw an internal error under the discount field and a routine typo was logged as an internal fault. The pricing engine's rejection is now a typed error, which the API boundary maps to 400 carrying the message. The message is still the same for every rejection reason, deliberately, so the endpoint cannot be used to enumerate which codes exist. Affects `GET /api/v1/vm/{id}/renew`, `GET /api/v1/subscriptions/{id}/renew` and their `/quote` variants.

- **A VM that moved between hosts is no longer rebuilt — or damaged — by the periodic check** — the worker read a VM's state from the host recorded in the database and, on any failure, concluded the VM did not exist and ran the spawn pipeline. A VM absent from its recorded host is far more often one whose placement drifted (a hand-run migration, or one that failed after the disk had moved) than one that was destroyed, so this tried to build a second copy of a live customer VM. It failed only because Proxmox ids are cluster-wide (`VM 2004 already exists on node 'pve2'`), and the failed spawn's rollback then reset the VM's MAC to the `ff:ff:ff:ff:ff:ff` placeholder — the address its static ARP, firewall and SLAAC address derive from, and the value every "has this VM been provisioned?" check reads. The check no longer cares which host a VM is on: it locates the VM across the hosts, corrects `host_id`/`disk_id` (recorded in VM history), and reads the state from the host that actually has it in the same pass. A rebuild now requires that every enabled host answered and none of them has the VM; a VM seen on two hosts, or a fleet with an unreachable host, is never rebuilt.

  Two rollback steps were destroying data on such a re-run and now undo only what that run created: the MAC is restored to whatever the pipeline found rather than the placeholder, and only IP assignments inserted by that run are removed — previously **every** assignment of the VM was hard-deleted, taking its addresses, static ARP and DNS records with it. A VM already carrying the placeholder MAC has it restored from the host's `net0` by the placement reconcile job, so machines damaged by the old behaviour repair themselves.

- **Migrating a VM between Proxmox nodes with local storage no longer fails** — `POST /api/admin/v1/vms/{id}/migrate` treated a destination pool with the source's name as the *same* storage and omitted `with-local-disks`, so the hypervisor refused the move outright (`can't migrate local disk 'local-zfs:vm-2004-disk-0': can't live migrate attached local disks without with-local-disks option`) and the queued job retried forever. A pool called `local-zfs` exists on every node but is node-local, and only the node can tell which volumes the destination cannot reach; the API now asks it (the same migration-precondition call the Proxmox UI's migrate dialog makes) and copies the disks into the same-named pool on the far side. VMs on genuinely shared storage still migrate without a copy.

### Added

- **VM history entries now carry what actually changed.** `GET /api/admin/v1/vms/{id}/history` and `GET /api/admin/v1/vms/{id}/history/{history_id}` gain `previous_state`, `new_state` and `metadata` as JSON objects (or `null`), so a client can diff an entry instead of parsing the free-text `description`. The columns were always JSON — written by `VmHistoryLogger` — and were previously dropped from the response on the assumption they were opaque binary. They contain only ids, VM states, expiry timestamps and payment amounts; no credentials. An unparseable stored blob is reported as `null` rather than failing the request. Permission is unchanged (`virtual_machines::view`).

- **The support agent no longer calls the admin API — every tool reads the database directly.** The email and Nostr channels previously ran on an HTTP client signing NIP-98 requests with an **admin nsec**, which meant a support process on the internet held a credential that could read and write every account on the platform, and a prompt injection was bounded only by that credential's permissions. There is now one executor, backed by the database, shared by every channel; the admin client, its nsec signer and the `db` cargo feature are gone. Two operational consequences:

  - **The standalone agent's configuration changed.** `admin-api-url` and `user-api-url` are replaced by `db` (a MySQL connection string) and an optional `encryption` key file — or the `LNVPS_ENCRYPTION_KEY` environment variable, the same one the API uses — without which the encrypted columns (a user's email, SSH key material, saved payment instruments) cannot be read. Give the agent a **read-only** database user unless the deployment wants the app-deployment start/stop pair, which is the only tool that writes. It never migrates the schema.
  - **The agent can no longer extend, refund or delete a VM.** Those were implemented by calling the admin API; re-implementing them against the database would mean a second, divergent copy of the subscription-lifecycle and billing rules, driven by a language model, so the tools were removed from every set rather than reimplemented. The email channel now escalates those requests to a human instead of performing them. The executor still refuses them explicitly, because a model can name a tool it was never offered. Everything else the email/Nostr channels could do, they still can — and they gain the tools that previously had no admin endpoint behind them (SSH keys, saved payment methods, VM firewall rules, hypervisor metrics, IP-space subscriptions), because there is no longer an API surface to be missing.

- **The support agent can now see every product a customer holds.** Its account-scoped tools covered VMs and nothing else, so a question about a subscription, a managed app, a referral or a marketplace node was answered from the model's memory or refused — and `list_vm_payments` reaches payments only *through* a VM, which cannot answer "what am I paying for" on an account that holds several products. New tools (all channels, since they all read the same database): `list_my_subscriptions` / `get_subscription_details` / `list_subscription_payments` (the object that actually expires and renews, with each line item resolved to the VM, deployment, IP range or ASN it bills for, and a billing state that distinguishes never-paid from lapsed — they need opposite answers); `list_my_app_deployments` / `get_app_deployment_details` plus reversible `start_app_deployment` / `stop_app_deployment`; `get_my_referral` / `list_referral_usage`; `get_my_marketplace_operator` (node approval status and last health check, which is the answer to "why is my node idle"); `list_my_ip_subscriptions`;; `list_my_ssh_keys`; `list_my_payment_methods`; `list_vm_firewall_rules`; and `get_vm_metrics`. Only the reversible workload controls (`start_vm` / `stop_vm` / `restart_vm` / `start_app_deployment` / `stop_app_deployment`) are live-chat only, being useful precisely where a human is waiting on the other end.

  Redactions are enforced per projection and tested by field *name* as well as by value: no decrypted app configuration (the admin deployment endpoint returns it, and it is stripped before the model sees it), no SSH key material, no processor references or card numbers, no marketplace node token version or libvirt certificate, no referral payout preimage. Ownership is re-checked on every id the model supplies, in the executor rather than in the prompt: a `vm_id`, `subscription_id` or `deployment_id` is attacker-influencable, and the narrower tool list advertised to a guest is not a control because a model can name a tool it was never given.

- **The support agent can now quote prices, including custom ("build your own") VMs.** Its catalogue tools previously listed plans with **no price at all** — specs and a region id — so every pricing question was answered from the model's memory or refused, and custom pricing was invisible to it entirely. `list_templates` now returns each plan's cost plan (amount, currency, billing interval) plus conversions to the other supported currencies, along with the included IPv4/IPv6 counts, CPU manufacturer/architecture/features, disk interface, and the IOPS / throughput / bandwidth / CPU caps (reported as `uncapped` rather than omitted, since a missing field reads to a model as "unknown"). Three tools are new, all available to logged-out visitors because pre-sales is who asks: `list_custom_pricing` (per-core, per-GB memory, per-GB disk by type/interface, per-IP costs and the ranges each may be ordered in), `price_custom_vm` (an exact quote for a configuration, validated through the same code path as the order endpoint, so an out-of-range spec returns the allowed range instead of a price nobody can order at), and `get_exchange_rate` (currency conversion, so the model never does the arithmetic itself). `list_regions` now also names the company that bills each region and its country; `list_os_images` adds CPU architecture and release date. The managed-app catalogue is exposed the same way (`list_apps`, `get_app_details`, `list_app_tags`), with each app's price, setup fee, resource footprint and — computed from real cluster capacity — the regions it can currently be deployed to, so the agent does not offer an app in a region that would reject the order. Every amount is returned in minor units *and* as a formatted value, and quotes state that tax and payment processing fees are extra. No REST endpoint changed — this is what the agent behind `WebSocket /api/v1/support/chat` and the email/Nostr channels can see.

- **Support chat can serve logged-out visitors** (issue #389) — `WebSocket /api/v1/support/chat` accepts a connection carrying **no** `ticket`/`auth` parameter as an anonymous guest session, so a pre-sales question on a public page no longer requires connecting a Nostr signer first (nor minting a throwaway key, which put a junk row in `users` per curious visitor). It is **on** wherever an agent is configured, and turned off with `agent.allow-anonymous: false` to serve only logged-in customers; each anonymous turn costs model tokens with no account to attribute the spend to, which is what the caps below bound. A guest gets the public catalogue tools only — regions, templates, OS images, terms — with no account context in the prompt; every account-scoped tool is refused by the executor itself, not merely omitted from the advertised tool list, since a model can name a tool it was never given. An *invalid* credential is still an error rather than a silent downgrade to guest.

  The server issues an opaque session id as the first frame, `session`, carrying an `id`; reconnecting with `?guest=<id>` resumes that transcript, which the frontend needs because a turn can run for minutes and idle proxies cut the socket. Treat the id as a bearer token — whoever holds it reads that conversation — and note an id this server did not issue is ignored in favour of a fresh one, so a client may reconnect blindly. Authenticated sessions never receive this frame.

  Abuse controls, since this is unauthenticated: a lower per-connection message cap (`agent.anonymous-max-turns-per-connection`, default 10 against the authenticated 50) plus per-client-IP caps on connections and on messages per hour (`agent.anonymous-connections-per-hour` / `anonymous-messages-per-hour`, defaults 20/60) that reconnecting does not reset. Limits are per API process, so several replicas multiply them.

  For discoverability, a plain `GET` on the chat path (no upgrade headers) now answers `{"available": bool, "anonymous": bool}` instead of failing the upgrade — 200 when an agent is configured, 404 when not, so the existing "non-404 means chat exists" probe still works. Check `anonymous` before rendering a chat box on a public page, or it will render one that always refuses.

- **Bulk messages can be targeted at a subset of customers** (issue #387) — `POST /api/admin/v1/users/bulk-message` takes an optional `target` (`user_ids`, `vm_ids`, `host_ids`, `region_ids`), unioned and de-duplicated by user, so host- or region-scoped maintenance can be announced through the platform instead of by hand over raw SMTP. Omitting `target` keeps the previous behaviour (every active customer). An optional `dry_run: true` resolves the recipient list and returns it without sending anything. The response now always reports the blast radius: `recipient_count`, `reachable_count`, per-channel `channel_counts`, and `unreachable_users` — users the filter matched that have **no** contact method at all, previously dropped in silence. Delivery still fans out over each user's own preferences (email, NIP-17, Telegram, WhatsApp), and the job result carries sent/failed/unreachable/matched counts to the `/jobs/feedback` stream. A `target` containing only empty lists is rejected rather than treated as "everyone". Unchanged permission: `users::update`.

- **Admin payment rows expose the discount that was applied** (issue #384) — `AdminVmPaymentInfo` and `AdminSubscriptionPaymentInfo` gain an optional `discount` object (`discount_id`, `code`, `amount_off`, `currency`, `settled`), so a discounted payment is no longer indistinguishable from a plain cheaper one in a VM's payment history or a subscription's payments. Affects `GET /api/admin/v1/vms/{vm_id}/payments`, `GET /api/admin/v1/vms/{vm_id}/payments/{payment_id}`, `POST /api/admin/v1/vms/{vm_id}/payments/{payment_id}/complete`, `GET /api/admin/v1/subscriptions/{subscription_id}/payments`, `GET /api/admin/v1/subscription_payments/{hex_id}` and `POST /api/admin/v1/subscription_payments/{hex_id}/complete`. The key is omitted entirely when no discount was used, and `amount` remains net of the discount. Listings resolve the whole page's discounts in one query, so the field costs no extra round trip per row.

- **Renewals can be priced without creating a payment** (issue #383) — `GET /api/v1/vm/{id}/renew/quote` and `GET /api/v1/subscriptions/{id}/renew/quote` take the same `method` / `intervals` / `code` query as the renew endpoints and return the priced order (`amount`, `tax`, `processing_fee`, `currency`, `time`, and `discount` when a code was supplied), creating nothing: no payment row, no Lightning invoice, no Revolut order. Pricing runs through the same code path as the renewal itself, so a quote cannot drift from what is charged, and the same validation applies (interval bounds, prepay horizon, host sunset, minimum amount).

  This is what makes a discount code usable in a checkout: the saving can now be shown *before* the customer commits, instead of the only way to price a code being to mint a real invoice on every keystroke. An unusable code fails the quote with the same error as the renewal, so a bad code is never silently dropped; quoting never consumes a usage limit, which is only taken at settlement, so a one-per-customer code stays quotable. It also removes the need for clients to re-implement VAT and processing-fee arithmetic to show an order summary.

  `method` additionally accepts the off-session values `saved` and `nwc` — priced as `revolut` and `lightning` — so a saved card or NWC wallet can be priced without a client mapping it back to an interactive method (and without risking a charge while doing so).

- **Discount engine (admin side)** — discount campaigns are now managed through `/api/admin/v1/discounts` (new `discount` RBAC resource: list/get/create/update/delete, plus `GET /api/admin/v1/discounts/{id}/redemptions` and `POST /api/admin/v1/discounts/preview`). A discount's eligibility **and** its effect are a single CEL expression returning a decision map — `{'percent': 10}`, `order.amount >= 10000 ? {'amount': 500, 'currency': 'EUR'} : {}` — so tiered and threshold offers need no new column each time a campaign shape changes. Only the integrity guards (validity window, total usage limit, per-user limit) are columns, because they need atomic enforcement at redemption and cannot be counted inside a side-effect-free expression.

  A rule sees the order's **line items** (`order.items`), each typed by the product it bills for and carrying that product's own properties — a VM line's plan, region, cores, memory, disk and included addresses; an app's catalog id and cluster; an IP range's CIDR — plus each line's `amount` and `setup_amount`, converted into the payment currency so a rule never juggles two currencies. So an offer can be aimed at a plan, a machine size, a region or a whole product type (`order.items.exists(i, i.type == 'vm' && i.template_id == 3)`), rather than at a single scalar the engine picked on the rule's behalf. A line's `type` is always accurate; detail that does not exist yet — an IP range is allocated only when the first payment settles — is null rather than the line being omitted.

  Whatever the expression returns is clamped in Rust: percent to `0..=100`, a fixed amount to `>= 0` and never more than the order total, with a non-decision return type (a bare `10`, a string) rejected outright rather than guessed at. A rule can therefore never over-discount an order, and a broken rule applies no discount instead of failing the customer's payment. Note that CEL map keys must be **quoted** (`{'percent': 10}`): a bare `{percent: 10}` is a variable reference, not a key. `POST /api/admin/v1/discounts/preview` evaluates a rule against a sample order without saving, so raw CEL can be checked before customers meet it.

  Customers apply a code with the new `code` query parameter on `GET /api/v1/vm/{id}/renew` and `GET /api/v1/subscriptions/{id}/renew`. The discount is subtracted from the order before VAT and the processing fee are computed — so a customer is never taxed on money they do not pay — and the payment's `amount`/`tax` are already net of it, with a new `discount` field describing what was taken off. A code that cannot be used **fails the request** instead of quietly invoicing full price: the customer typed something and is owed an answer. Referral commission needs no change and follows the discounted amount, because it is computed from the recorded payment amount.

  A discounted order is priced fresh rather than reusing a pending invoice: entering a code when an unpaid invoice already exists produces a new, cheaper one instead of handing back the full-price invoice.

  The discount applies to the payment it is used on; renewals bill at list price. Limits are consumed at **settlement**, not when the invoice is created, so an abandoned invoice does not burn a campaign's stock or lock the customer out of a one-per-customer offer. Settlement is idempotent across every payment method, including replayed webhooks.

- **A user's tax treatment is now visible from the admin API** — `GET /api/admin/v1/users/{id}/tax` (`users::view`) runs the same determination the pricing engine uses and returns it per seller company: the rate, the treatment (`domestic`, `oss_b2c`, `reverse_charge`, `out_of_scope`, `undetermined_default`), the resolved place of supply, and the evidence that decided it (declared country, IP country, customer VAT number). Live rather than read back from the last payment, so it answers "what would we charge them now" — the question actually asked when a customer disputes VAT or has just supplied a VAT number.

  A rate is not a property of a user, which is why the response is a list: the seller's country is half of the rule, so the same customer is taxed differently by different companies. The treatment matters more than the number — a `0.0` from a cross-border reverse charge and a `0.0` from a non-EU customer are unrelated situations, and a bare country VAT percentage would misreport both.

  The admin API now also loads and refreshes the EU VAT rate table daily, as the public API already did; it previously had none, so any rate it computed would have been 0%. `rates_loaded` reports whether the table is populated, so an empty one is never presented as "this customer pays no VAT".

- **Listing support-agent conversations returned a 500.** `COUNT(*)` is a signed `BIGINT` in MariaDB while `message_count` decodes as `u64`, so every call to `GET /api/admin/v1/agent/conversations` and `GET .../{id}` failed with `mismatched types; Rust type u64 (as SQL type BIGINT UNSIGNED) is not compatible with SQL type BIGINT`. The aggregates are now cast to `UNSIGNED`. The same fault was latent in `max_agent_message_id`, which bounds the watermark on `PATCH`. Neither could be caught by the unit tests: the mock returns Rust values and never decodes a SQL type, so the endpoints were only ever exercised against something that could not reproduce it. Both paths now have e2e coverage against a real database.

- **Support-agent conversations can now be read and their memory managed from the admin API.** `GET /api/admin/v1/agent/conversations` (filterable by `user_id` and by `conversation_key` substring), `GET .../{id}`, and `GET .../{id}/messages` (oldest first, content decrypted, tool calls and tool results included) — all `support_agent::view`. Until now the only way to see what the agent had told a customer was to query the database directly. The transcript stays append-only, because it is also the training corpus: nothing here edits or deletes a message.

  `PATCH /api/admin/v1/agent/conversations/{id}` (`support_agent::update`) changes what the agent *remembers* — the `summary` and `compacted_upto` watermark — which is a different thing from the transcript. Those two fields are exactly what the model replays on the next turn, so rewriting or clearing them is the fix when an agent has formed a wrong belief about a customer, and it leaves every message row untouched. Clearing `summary` alone is the safe reset: the agent forgets what it believed while the next prompt stays bounded by the messages above the watermark. Setting `compacted_upto` to `0` replays the **entire** transcript and is slow and expensive on a long thread. A watermark past the last message is rejected — it would suppress everything appended afterwards and leave the agent permanently blind to that thread. Unlike the agent's own compaction, this endpoint may move the watermark backwards, which is the point of an admin reset.

  `support_agent` is a new permission resource (granted to `super_admin` by migration), deliberately not folded into `users`: a transcript carries whatever a customer pasted into a support request, which is a wider disclosure than the account fields `users::view` implies. There is no message-content search — content is encrypted at rest, so the database cannot match against it — and public Nostr threads keep their own `nostr:` namespace in the listing's `kind`, since those are readable by the whole relay network while every other kind is private.

- **The route server now routes its tunnel pool's own blocks.** An address on a point-to-point interface does not route the rest of its prefix, so a route server holding `10.66.0.1/16` answered "network is unreachable" for every node in that pool — the peers were configured correctly and unreachable. Found by an end-to-end harness that builds both ends of a tunnel and sends real packets, not by review.

- **LNVPS can call a node** — `GET /api/admin/v1/marketplace/nodes/{id}/status` (admin, `marketplace_node::view`) returns what the node says about itself right now: daemon version, tunnel state and handshake age, bridge, forwarding, routed guest count, and the packet filter. Signed with LNVPS's existing nostr identity (`nostr.nsec` — the account customers DM for support, `npub1lnvps32qq2nvg75cqwflq4y6cmnzn55d26ypzjakpkp3khqcx2ns7t7vjj`), which the admin API now also reads; without it the endpoint answers that this deployment runs no marketplace rather than failing obscurely. One identity rather than a control key of its own: a separate secret would have to be generated, distributed to whoever builds the node binaries and kept in step with the value compiled into them, whereas this one is already published — an operator can check the key their node obeys against an account that publicly answers. Both ends of the call are authenticated — the request is a NIP-98 event signed with LNVPS's control key, which the node checks against a public key compiled into its binary, and the node's TLS certificate is checked against the fingerprint it registered. There is no CA: the node is self-signed and its name is an address inside a tunnel, so what is verified is the pin. Without server authentication anything able to answer on that address — a guest that grabbed the IP, a mistake on the route server — could report that a VM is running when it is not.

- **A node's status now reports the packet filter around its guests** — `GET /status` on the node control API gains `dataplane.firewall`: whether the machine has a working nftables, whether LNVPS's ruleset is loaded, whether guests are isolated from each other at layer 2, how many guest bindings are enforced, which ruleset the *kernel* is running (a tag read back out of a rule comment, not remembered by the daemon), and how many packets have been dropped for claiming an address the guest was not assigned. That last number is the only one here that says something about a customer rather than a node: a guest that is spoofing is either compromised or hostile, and LNVPS would rather learn it from a counter than from an upstream abuse report. A node whose filter is not loaded now reports itself **unhealthy** — an unfiltered node is one where any guest can be any other, which is worse than a node carrying nobody.

- **A node is only opened to customers once a VM has actually run on it** — LNVPS periodically builds a real VM on an approved marketplace node through the ordinary customer path, logs in over the tunnel, measures what a customer would get, destroys it, and enables the backing host only if that passed. Until now the only thing between an operator's machine and a paying customer was that the machine answered questions about itself; everything LNVPS can see from outside is what the node chooses to report, and a VM having run there is not. Measured: time from asking for the VM to having a shell; memory the guest could allocate **and touch** (allocation alone proves nothing where the host overcommits — a node reselling four times its RAM passes an allocation check and fails this); and disk write/read rates with the cache bypassed (an operator can present an NVMe node backed by a network volume, which is visible as a rate and invisible as a specification). Results are a **series**, at `GET /api/admin/v1/marketplace/nodes/{id}/health` — one bad run is a bad afternoon, a trend is a node to act on — and each row records the shape and image it measured, because regions sell different templates and raw numbers across them would rank machines by what we happened to ask for. Failures are rows too: a node that never completes a probe is indistinguishable from one nobody probed unless they are written down. Nothing about the probe VM is stored: it lives in the API's memory and the node's libvirt, is destroyed on every path out including a panic, and its id is in a reserved range no customer VM can reach — domains are named from the VM id, so a probe sharing one would delete a customer's disk. Probes are IPv6-only (IPv4 is the scarce resource the marketplace exists to stretch), each node is left alone for six hours afterwards including after a failure (retrying immediately hammers the machine least able to cope), and one node is probed per sweep so the fleet is never asked at once.

- **LNVPS can run VMs on a marketplace node** — the node runs a libvirtd LNVPS drives over the tunnel, so a marketplace node becomes just another libvirt host and every existing flow (create, start, stop, resize, migrate, terminal, stats) works unchanged instead of being reimplemented against a node-specific protocol. Which libvirtd it is, is the whole design: it runs **inside the node's data plane network namespace**, because a domain's tap device is created in the namespace of the libvirtd that starts it and the guest bridge only exists there; it is a **second instance rather than the operator's**, because moving theirs into our namespace would take the networking off every VM they already run and put their domains inside the connection LNVPS drives; and it gets a **private mount namespace** as well, because two system libvirtds sharing `/var/lib/libvirt` contend over domain state, storage pools and sockets. Access is **TLS with a client certificate**, which is load-bearing rather than belt-and-braces: the guest bridge shares a namespace with the tunnel interface, so a customer VM can address the listener, and the certificate is what makes a packet-filter regression survivable instead of handing a guest control of the node and every other customer on it. libvirtd binds the node's tunnel address only — the machine's other interfaces are the operator's LAN and their uplink.

  Proving this against a real libvirtd found four things no unit test could: libvirtd's default pid file is `/run/libvirtd.pid`, which is *not* inside the private `/run/libvirt` — so the operator's daemon holds the lock and ours refuses to start; libvirt will not serve a CA certificate as its own leaf, so the node now roots a one-certificate chain (a CA it registers, a server certificate it signs) rather than presenting a self-signed CA; **both** ends validate the certificate they present against the same file they verify the far end with, so each side's trust file carries two CAs; and the node's own packet filter accepted only ICMP on the tunnel, which had been dropping **every** call LNVPS made to a node — the control API included — while the node looked perfectly healthy.

  Each node is verified against **the certificate it registered** (`POST /api/v1/node/libvirt`, node token), not against a fleet CA: one CA would mean any node's certificate satisfies a connection to any other, which is exactly the substitution being prevented — something else answering on a node's tunnel address and reporting that a customer's VM is fine when it is not. The whole certificate is stored where the control API stores only a fingerprint, because libvirt verifies a chain rather than pinning a hash. Nodes re-present their certificate on every poll, so rotation (a node restored from backup, a tunnel address that moved) is the same call, and an API host that loses its per-node trust directory repairs itself within one poll interval. LNVPS holds **one client certificate for the fleet** — every node is told to accept exactly one DN, and a per-node client certificate would be a per-node key to issue, ship and rotate for a decision that is identical everywhere; the CA that signs it is delivered in the node's data-plane document, so rotating it takes one poll rather than a new node package. With no client identity configured, nodes are still enrolled and networked but no VM is placed on one and the node is told to leave libvirt alone, because an unauthenticated listener on an address the node's own guests can reach is worse than not having the feature.

- **A node can fetch its whole data plane in one document** — `GET /api/v1/node/dataplane` (node token) returns the tunnel it already gets from `/node/tunnel`, plus the gateway addresses the node must answer for, and the guests assigned to it (address, gateway, MAC). One call rather than three because the node applies these together or not at all: a bridge with no tunnel carries nothing, a tunnel with no guest routes carries nothing back, and a document that can be half-fetched is a data plane that can be half-applied. The guest list is also the anti-spoof list — an address not in it is not that node's to send from. The gateway is the one the guest was actually configured with, taken from its IP range: it belongs to the range rather than to the node, and the guest believes it is on-link, so the node has to answer for it rather than invent one.

- **A node takes one address, not a point-to-point link** — `address4`/`address6` in the tunnel response are now a `/32` and a `/128`, and `gateway4`/`gateway6` are one address shared by every node on the pool rather than a per-node link address. WireGuard is layer 3 and point-to-point: the node needs no gateway on its own side (`ip route add default dev wg0` suffices), so a `/31` spent two addresses describing something that needs one — and forced the route server to carry one address per node on a single interface, thousands of them on a /16 pool. Pool capacity is reported accordingly: a /24 places 253 nodes (256 less the block's network address, the route server's address after it, and the broadcast address) where it previously reported 128 links.

- **A marketplace node's tunnel is now actually configured on the route server** — allocating a tunnel (`POST /api/v1/node/tunnel`) previously wrote down addresses and a key and stopped there; the node's peer is now pushed to the route server, so the tunnel carries traffic instead of only existing on paper. The peer's `AllowedIPs` is the node's own inner addresses plus exactly the guest addresses LNVPS assigned to it, which is also the anti-spoof boundary: WireGuard drops an inbound packet whose source is not on that list, so a node cannot source traffic as another node's customer. The route server takes an address on each point-to-point link, and each guest address is routed down the interface — `AllowedIPs` decides which *peer* a packet already headed for the tunnel belongs to, it does not put the packet there. Peers are also reconciled on the routine router poll, so an address assigned to a guest since the last push, a peer wiped by a route-server reboot, and a stale key nobody removed are all corrected without an admin doing anything; the reconcile reports what had drifted rather than quietly fixing it. The backing host stays **disabled** — a configured peer is still not a proven path, and the health gate that enables it comes with the node-side data plane.

- **Marketplace nodes get a data plane** — an approved node can now ask for the WireGuard tunnel that carries its guests' traffic back to an LNVPS route server. `POST /api/v1/node/tunnel` (node token) presents the node's WireGuard **public** key and returns everything needed to bring the tunnel up: its own inner addresses (a `/32` and a `/128`), the route server's address on the pool, the server's public key, the `host:port` to dial, the keepalive and the MTU; `GET /api/v1/node/tunnel` reads the same back after a restart. The private key is generated on the node and never leaves it, which is why the key is presented rather than issued. Idempotent: retrying returns the allocation already made, and a node that presents a *new* key (restored from backup, state directory lost) is re-pinned in place without its addresses moving — refusing would leave a machine that can never be reached again. Addresses come from a new **tunnel pool**, administered at `GET/POST /api/admin/v1/tunnel_pools`, `GET/PATCH/DELETE /api/admin/v1/tunnel_pools/{id}` and `POST /api/admin/v1/tunnel_pools/{id}/sync` under the `router` resource: a route server, a region, the socket the data plane listens on (`listen_addr` + `listen_port`, unique per route server because a WireGuard interface listens on every local address at its port) and the v4/v6 blocks that node addresses are carved from. **LNVPS manages the interface end to end**: creating a pool generates its keypair, stores the private key encrypted and configures the interface on the route server; editing re-applies it; deleting removes it. The interface is named `wgln<id>` from the pool's id and is not settable — a route server also carries interfaces LNVPS did not configure, and a fixed prefix keeps a managed one from being confused with, or clobbering, those. An admin never pastes key material for an interface they set up by hand, so standing up a new route server is an API call rather than a manual job with a database row bolted on afterwards — an existing interface can still be adopted by supplying its private key, and the public half is always derived, never accepted. The private key is never returned by any endpoint. Allocation also fills in the blank control address that node approval leaves on the backing host — the node's control API is only reachable through the tunnel. The host stays **disabled**: an allocation is paperwork, not a working tunnel, and the peer is not configured on the route server until the next increment.

- **Admin approval for marketplace nodes** — operator-registered hardware can now be reviewed and admitted to the fleet. `GET /api/admin/v1/marketplace/nodes` (filterable by `status`/`operator_id`) is the review queue, `POST /api/admin/v1/marketplace/nodes/{id}/approve` admits a node, `PATCH /api/admin/v1/marketplace/nodes/{id}` suspends, drains or re-tiers it, and `DELETE /api/admin/v1/marketplace/nodes/{id}` rejects a registration outright — there is no `rejected` state, so an operator can fix what was wrong and register the same machine again. Approval is the **only** transition into `approved` and the only place the gates are checked: a node with no pinned TLS certificate cannot be reached and is refused, and where the region's company charges a listing fee, that fee must be paid *to that company* — a fee paid to a cheaper company does not list hardware elsewhere. Approving a node creates its backing host **disabled and with an empty control address**, because the node is reachable only over a data-plane tunnel that does not exist yet; capacity defaults to zero rather than being guessed, since real figures arrive with node telemetry. Suspending or draining also disables that host, so placement stops immediately instead of depending on the scheduler learning about node status. Two new permission resources, deliberately separate: `marketplace_node` (placement state) and `marketplace_operator` (revenue-share override and payout configuration, via `GET`/`PATCH /api/admin/v1/marketplace/operators[/{id}]`) — stopping a misbehaving node should not require the ability to change what someone is paid.

- **Single-use tickets for WebSocket and HTML authentication** — new endpoints `POST /api/v1/auth/ticket` and `POST /api/admin/v1/auth/ticket` mint a short-lived (30s), single-use, path-scoped credential for the endpoints a browser cannot send an `Authorization` header to. Body is `{ "path": "/api/v1/vm/7/console" }`; the response is `{ "ticket": "...", "expires_in": 30 }`, passed to the target as `?ticket=<ticket>`. Supported on `/api/v1/vm/{id}/console`, `/api/v1/payment/{id}/invoice`, `/api/v1/support/chat` and `/api/admin/v1/jobs/feedback`; tickets cannot be minted for any other path. A ticket in an access log, proxy log or browser history is inert once used, and unlike a NIP-98 event it is not a signature made by the user's identity key. **The legacy `?auth=<base64_nip98_event>` form still works and is unchanged for existing clients, but is deprecated — please migrate to tickets.** A ticket does not grant access: the target endpoint still performs its own ownership/permission check.

- **Log out everywhere** — new endpoint `DELETE /api/v1/account/sessions` invalidates every outstanding session (Bearer) token for the account by bumping its session version. Nostr (NIP-98) authentication is unaffected, having no server-issued token to revoke.

- **VM migration between hosts** — new endpoint `POST /api/admin/v1/vms/{id}/migrate` moves a VM to another host (issue #66). Body is `{ "target_host_id": u64, "live": bool?, "reason": string? }`; `live` attempts an online (Proxmox) migration, otherwise the VM is stopped, moved and started again on the destination. The work runs on the worker and is pre-flighted there: the target must be enabled, in the same region (a VM's IP assignments are not rewritten, so a cross-region move would strand them), of the same hypervisor kind and CPU architecture, and have free CPU, memory and disk for the VM. The destination disk is the pool with the same name as the source where one exists — on shared or mirrored storage that means nothing is copied — otherwise the emptiest pool with room, copied across. `vm.host_id`/`vm.disk_id` change only after the hypervisor confirms the move, the firewall ruleset is re-applied on the destination, and the move is recorded in VM history under the new `migrated` action type. Requires `virtual_machines::update`. Implemented for Proxmox hosts; other host kinds return a clear "not supported" error.

- **VM placement drift is detected and corrected automatically** — a `ReconcileVmHosts` job now runs every 10 minutes, lists the VMs on every reachable host and re-points `vm.host_id`/`vm.disk_id` at the host that actually has each VM. A VM migrated outside this API (a `qm migrate`, or a drag in the Proxmox UI) previously left the database aiming every lifecycle operation — start, stop, reinstall, firewall sync, state polling — at a node that no longer had the VM, with no signal that anything was wrong. Corrections are recorded in VM history as a `migrated` action with `detected: true` and raise an admin notification. Hosts that cannot be polled are skipped rather than treated as empty, and a VM found on two hosts at once (a leftover copy after a migration) is reported but never reconciled, so the record cannot flap between them.

- **Admins can extend any subscription, not just VMs** — new endpoint `PUT /api/admin/v1/subscriptions/{id}/extend` grants free time on a subscription of any type (managed apps, IP ranges, ASN sponsoring, DNS hosting, VPS), the counterpart of the existing `PUT /api/admin/v1/vms/{id}/extend` which could only be aimed at a VM. Body is `{ "days": 1-365, "reason": string? }`; the days are added to the current `expires` (or to now when there is none), so unused paid time is never lost and a lapsed subscription is extended from where it lapsed. As with the VM endpoint, granting time sets `is_setup`/`is_active` so the lifecycle worker does not tear the resource down anyway, and a `CheckSubscriptions` job is dispatched to pick up the new expiry. No payment row is written — this is granted time, not a settlement. Requires `subscriptions::update`. Returns the updated subscription with its line items.

- **Custom VM price states its billing period** (issue #302) — `POST /api/v1/vm/custom-template/price` gains `interval_amount` and `interval_type`, the same shape a standard template's cost plan already uses. Custom builds renew monthly, so the values are always `1` and `"month"`; the point is that a client no longer has to hard-code the period to render a recurring price. Additive: no existing field changed.

- **Live chat with the AI support agent** — `WebSocket /api/v1/support/chat` opens a streaming conversation with the support agent. Authentication matches the VM console endpoint (`?auth=<base64_nip98_event>`, signed over the chat path). Messages are sent as plain text frames; replies stream back as JSON event frames (`token`, `final`, `error`), with exactly one terminal `final`/`error` per message sent. Callers holding the `users:view` admin permission additionally receive `tool_start` / `tool_done` frames describing the agent's internal lookups; ordinary customers receive only the reply content. The agent can read the caller's account, VMs, payments and VM history, and can start/stop/restart their VMs — it **cannot** extend, refund or delete a VM, and refers those to email support. Per-message length (4000 chars) and per-connection message count (50) are capped. Conversation history is persisted per account and shared with the email support channel; public Nostr threads are kept separate. The endpoint requires the server to be built with the `agent` feature and to have an agent configured, and otherwise refuses connections.

- **Admin can create a custom-spec VM** (issue #335) — `POST /api/admin/v1/vms/custom` creates a VM from an arbitrary spec for any user, billed against a custom pricing plan, instead of only from the fixed template catalog. Body is the customer custom-order shape plus `user_id`/`reason`: `pricing_id` (also decides the region), `cpu`, `memory` and `disk` in bytes, `disk_type`, `disk_interface`, optional `cpu_mfg`/`cpu_arch`/`cpu_feature`, `image_id`, `ssh_key_id` (must belong to the target user), optional `ref_code`. Returns `{ "job_id": string }`; the VM is created unpaid like a customer order. Unknown enum spellings are `400` and are never defaulted. Additive: `POST /api/admin/v1/vms` (template path) is unchanged.

- **A VM can hold more than one address per family** (issue #343) — every assignment is now placed on the VM's single NIC through a per-VM cloud-init network config (`cicustom network=`), instead of the built-in `ipconfig`, which carries only one IPv4 and one IPv6 per interface. A VM with one address per family is unaffected and keeps its existing `ipconfig`, so nothing already deployed is reconfigured. The interface is matched by MAC so the config does not depend on guest device naming; one default route per family is emitted (the first assignment's gateway wins, as before); a SLAAC range contributes router advertisement rather than a pinned address. No response shape changed — the offered maximum is now simply whatever an operator sets on the plan or template.

- **IP counts are a sellable dimension of an offer** (issue #105) — a VM offer now states how many addresses it includes instead of implying exactly one IPv4 plus an optional IPv6.
  - `ApiVmTemplate` (in `GET /api/v1/vm/templates`, `GET /api/v1/vm/{id}` and every VM listing) gains `ip4_count` and `ip6_count`. Additive; nothing existing changed shape.
  - `GET /api/v1/vm/custom-template` params gain `min_ip4`/`max_ip4`/`min_ip6`/`max_ip6`. `max_ip4` is already capped by what the region can actually supply, so a client can use it directly as a selector bound, and a plan whose `min_ip4` cannot be met is not listed at all.
  - `POST /api/v1/vm/custom-template` (and the price quote) accept `ip4_count`/`ip6_count`. Both default to `1` when omitted, so existing clients order exactly what they did before. Counts outside the plan's range are rejected. Cost is `count × ip4_cost` / `count × ip6_cost`, so the quote for a multi-address order is higher than before by exactly the extra addresses.
  - Custom VM billing now takes the counts from the ordered spec rather than counting the VM's current assignments. Existing VMs are migrated to the counts they currently hold, so no live renewal amount moves.
  - Provisioning allocates the stated number of addresses across the region's ranges. IPv4 is all-or-nothing: an order asking for addresses the region cannot supply fails instead of quietly getting fewer. IPv6 remains best-effort, unchanged — a region without an IPv6 range still provisions, and a SLAAC range yields one address per VM.
  - Admin: `ip4_count`/`ip6_count` on VM template create/update/read, and `min_ip4`/`max_ip4`/`min_ip6`/`max_ip6` on custom pricing create/update/read/copy. All default to 1, so no plan starts offering a choice until an operator widens it.

- **Guest disks get a dedicated QEMU IO thread** — VMs are now created with the `virtio-scsi-single` SCSI controller and `iothread=1` on their primary disk, instead of `virtio-scsi-pci` with no IO thread. Previously every guest's block IO was serialised through the main QEMU event loop alongside device emulation and networking, capping a VM at roughly a single thread of storage throughput regardless of how fast the underlying host pool was. Existing VMs converge on the new settings the next time their config is reconciled; because a SCSI controller change only takes effect at VM start, an already-running VM keeps its old behaviour until it is stopped and started (a reboot from inside the guest is not enough). No API shape changed and no customer action is required. `iothread` is ignored with a warning by `qemu-server` on controllers other than `virtio-scsi-single`, so a VM caught mid-transition is never left in an invalid state.

- **`host_ssh_keys` on VM status** (issue #154) — `GET /api/v1/vm/{id}` and `GET /api/v1/vm` now return the VM's own SSH host keys as `[{ key_type, public_key, fingerprint_sha256 }]`, so a client can verify the host on first connect instead of accepting whatever key answers. The list is empty until the keys are captured (scanned from the host once the VM is running, public keys only) and is re-captured after a reinstall, which regenerates them. Additive: no existing field changed. Not to be confused with `ssh_key`, which is the customer's authorized key.

### Added

- **Fiat-settled referral commission can be paid out automatically** (issue #312) — commission earned in a fiat currency was only ever payable by hand. When `min-fiat-payout-sats` is set under `[referral]`, the worker now quotes the balance against BTC at send time, pays it over Lightning, and records both sides on the payout (`amount`/`currency` = fiat discharged, `sent_amount`/`sent_currency` = sats sent, `rate`/`rate_collected` = the quote). Only the value of the whole sats sent is discharged, so the sub-sat remainder stays owed. Off by default — omit the key and fiat commission accrues for manual payout as before. On-chain referrers are excluded (their batched network fee is split in sats and cannot be charged against a fiat balance). No response shape changed.

### Added

- **`GET /api/admin/v1/referrals/{id}` now returns the outstanding balance** — the response previously showed only gross `earned` per currency, so working out whether a referrer was near their payout threshold meant netting the payout list by hand. Two additive fields: `balances` (per settled currency: `earned`, `settled` — paid **and** reserved, amount + fee — `outstanding`, and `outstanding_msat` valued at the current rate, `null` when no rate is available) and `outstanding_total_msat`, the total the payout threshold is judged against, directly comparable with `payout_threshold` × 1000. `earned` currency keys are now upper-cased so a mixed-case ledger is one balance instead of two. No existing field changed.

### Fixed

- **Referral payout thresholds now count every currency, not each one alone** — the minimum-payout threshold (the system minimum and your own `payout_threshold`) was applied to each balance separately, so a referrer owed a little BTC and a little fiat could clear the floor overall and still be paid neither, indefinitely. The threshold is now judged on the **total** outstanding commission valued in millisats (BTC plus every fiat balance at the current rate) for the kinds payable in that run, and when it clears, each balance is settled as before (still rounded down to whole sats, still netted per settled currency). Applies to Lightning/NWC payouts and the batched on-chain payout. No request or response shape changed.

- **Admin-completed subscription payments now run the same on-payment handling as a Lightning settlement** (issue #320) — `POST /api/admin/v1/subscription_payments/{id}/complete` marked the payment paid but skipped the subscription's line item handlers, so a managed app never got its instant reconcile (it waited for the operator's next poll) and an Upgrade payment was marked paid without the upgrade ever being applied. The endpoint now also dispatches the handling to the worker, and fails (rather than returning `200`) if that dispatch cannot be queued. Repeating the call on an already-paid payment re-queues the handling instead of returning `409`, so a failed dispatch is recoverable; it never extends the subscription twice. Response shape is unchanged.

- **`GET /api/v1/payment/{id}` now works for every subscription type** — it previously resolved the payer through the VM back-reference, so a payment for a managed app, IP range or other non-VPS subscription errored instead of returning. Ownership is now asserted on the subscription and the embedded `vm_id` is `0` for non-VPS payments (the endpoint remains deprecated in favour of `GET /api/v1/subscriptions/{id}/payments/{payment_id}`).

### Deprecated

- **VM-specific payment endpoints** — `GET /api/v1/vm/{id}/renew`, `GET /api/v1/vm/{id}/payments` and `GET /api/v1/payment/{id}` are superseded by the subscription APIs, which cover every product type rather than just VPS. Use `GET /api/v1/subscriptions/{id}/renew` and `GET /api/v1/subscriptions/{id}/payments` with the VM's `subscription_id` (returned on `ApiVmStatus`), and `GET /api/v1/subscriptions/{id}/payments/{payment_id}` (new, below) to poll a single payment. `GET /api/v1/payment/{id}` in particular can only resolve payments that belong to a VM subscription, so it cannot poll a managed app or IP range payment at all. All three still work and are unchanged; they will be removed in a future release. `GET /api/v1/payment/{id}/invoice`, `GET /api/v1/payment/methods` and the LNURL routes (`/api/v1/vm/{id}/lnurlp`, `/api/v1/vm/{id}/renew-lnurlp`) are **not** deprecated — the invoice route is the canonical invoice surface for all subscription types and the LNURL routes serve external wallets.

- **Per-response currency conversion arrays** (follows #230) — `other_price[]` on VM cost plans (`VmCostPlan`) and custom VM prices (`CustomVmPrice`), and `other_price[]` / `other_setup_fee[]` on `IpSpacePricing`, are now deprecated in favour of the single `GET /api/v1/exchange-rate` feed. They are still populated for backward compatibility but will be removed in a future release. Clients should compute conversions from the exchange-rate endpoint (`rates[B] / rates[A]`), which uses the same conversion source and precision.

### Changed

- **A managed app's persistent volume can grow but can no longer shrink, be removed or be renamed** (issue #292) — enforced when an app is updated through the admin API; `PATCH /api/admin/v1/apps/{id}` returns `400` when the incoming compose lowers a `volumes[].size`, or drops a `(service, volume name)` pair the stored compose declares. Kubernetes permits PVC expansion only, and the operator re-reads the catalog compose on every reconcile pass, so one shrinking edit puts every existing deployment of that app into a permanent `422 Forbidden: field can not be less than status.capacity` loop that the operator cannot walk back. Removals and renames fail differently and just as permanently: server-side apply cannot prune an object it merely stops applying, so the old PVC survives with the customer's data in it, unmounted and no longer counted against the app's storage — a rename is a remove plus an add, and orphans it the same way. Create is unaffected (there is no stored row to compare against), as is the operator, which keeps reconciling a row stored before this rule.

- **A managed-app service addressed as `name:port` by another service must declare `ports:`** (issue #281) — enforced when an app is created or updated through the admin API; `POST`/`PATCH /api/admin/v1/apps` returns `400` for a compose that points at a peer with no ports. The operator creates a Kubernetes Service — the only source of an in-namespace DNS name — only for a service with declared ports, so `postgres://buzz:…@db:5432/buzz` against a `db` that declares none is a hostname that does not resolve. The Buzz catalog app reached production this way and failed on its first connection with `Name or service not known`; the same defect was latent in `route96`, whose `db` is addressed at `db:3306` and declared no ports. Both documented composes now carry internal port blocks (`expose: none`, so nothing becomes publicly reachable).

  Authoring-time only, like the `${…}` rule beside it: an app definition stored before this keeps reconciling unchanged and is caught the next time an admin edits it. The live catalog rows need the same edit, which no migration performs — and because the operator re-reads the app's compose on every pass, updating the row repairs an already-deployed instance without re-ordering it.

- **Managed app config fields are validated against their declared `type`### Changed

- **Managed app config fields are validated against their declared `type`, and may declare a `pattern`** (issue #271) — **stricter validation on `POST /api/v1/app-deployments`, `PATCH /api/v1/app-deployments/{id}` and the admin app create/update endpoints.** An order that previously succeeded with a garbage value now returns `400`.

  `resolve_config` enforced `required` and unknown keys and never looked at `type`, so an `int` field accepted `abc`, a `bool` field accepted `maybe`, and a `string` field accepted anything at all. That is only a validation gap until an app is strict about the value: HAVEN panics on an `owner_npub` that is not an npub, so a single mistyped character was accepted at order time, charged for, and became a deployment that restarted forever with nothing on screen naming the field.

  `int` must now parse as a whole number and `bool` must be `true` or `false`. A field may also declare `pattern`, a regex the value must match **in full** (it is anchored automatically, so `npub1…` cannot admit a value with junk on the end); `type: file` is exempt, being arbitrary content by definition. Errors name the field's **label** — what the customer sees on the form — not its internal name.

  An empty submitted value for an `int` or `bool` field is treated as "not supplied" — it falls back to the field's default, or errors as required — because a form that posts every field sends `""` for the boxes nobody touched, and refusing those would fail an order over a field the app has a default for. An empty **string** is unchanged: blank is a legitimate value there.

  A `pattern` is compiled when the app is created or updated, so an invalid regex is the catalog author's error rather than a customer's failed order, and a declared `default` is checked against its own field at the same point. Existing app definitions are unaffected: no field declares a `pattern` yet, and the documented `owner_npub` (HAVEN) and `owner_pubkey` (Buzz) fields gain one in this release — the live catalog rows need the same edit, which no migration performs.

- **An app deployment's `status` now reports the workload, not the billing gate** (issue #276) — **`status` on `ApiAppDeployment` changes meaning; no field is added or removed.** The operator wrote `running` whenever the subscription was paid, the customer had not stopped the deployment, and the reconcile completed — nothing anywhere read the workload back. A database that aborted while initialising its data directory therefore reported `running` in the admin UI and on the customer's own page, continuously, while it crash-looped.

  `running` now requires every replica to be ready. A container the kubelet has given up on (`CrashLoopBackOff`, `ImagePullBackOff`, `ErrImagePull`, `CreateContainerConfigError`, `CreateContainerError`) reports `error`, with the failing service, that reason and the head of the container's last termination message in `status_message`. Anything else not yet ready reports `pending`, which is what a deployment coming up honestly is.

  **Clients that treated `running` as "provisioned successfully" will now see `pending` for the first seconds of a deployment's life and `error` for one that cannot start.** Both were previously reported as `running`. `stopped` is unchanged and still answers the billing/lifecycle question — pair it with `billing_state` (issue #253) to tell "customer stopped it" from "never paid". When the operator cannot reach the API server to read health, it leaves the stored status alone rather than guessing.

- **A managed-app service that declares `volumes:` must now declare `user:`** (issue #277) — enforced when an app is created or updated through the admin API; `POST`/`PATCH /api/admin/v1/apps` returns `400` for a compose that declares a data volume on a service with no user. Kubernetes chowns a freshly provisioned PVC to the pod's `fsGroup`, which the operator takes from the numeric compose `user:`; without one the volume mounts root-owned `0755` while the kubelet starts the container as whatever non-root UID the image names, so the app deploys, starts, and fails on its first write — on a fresh volume, every time, with nothing in the deployment's status saying so. `user: root` satisfies the rule: a root process can write to a root-owned volume.

  Authoring-time only. An app definition stored before this rule keeps reconciling exactly as it did (the rendered pod is unchanged); it is caught the next time an admin edits it. No documented catalog app is affected — all thirteen services with volumes already declare a user.

### Added

- **A custom domain is held until it is seen resolving to us** (issue #307) — setting `custom_domain` on a managed app deployment previously created its ingress rule and asked cert-manager for a certificate straight away, so a domain entered before its CNAME existed left an unservable rule and an HTTP-01 challenge that failed on every reconcile, spending the ACME account's failed-validation budget with nothing shown to the customer.

  The domain is still accepted immediately — the CNAME is usually created afterwards — but nothing serves it and no certificate is requested until the operator observes it resolving to the same address as the deployment's `hostname`. New boolean `custom_domain_verified` on `ApiAppDeployment` (`GET`/`PATCH /api/v1/app-deployments`, `/{id}`) and `AdminAppDeploymentInfo` reports which state it is in: `false` = held, `true` = served. It is always `false` when `custom_domain` is `null`.

  Additive; no existing field changes meaning. Changing the domain holds it again, on both the customer and admin `PATCH`. Verification is sticky once granted: a later resolver failure does not tear down a domain already being served. Domains set before this change are backfilled as verified, so nothing live goes dark. Surface the held state in the UI with the record to create — a `CNAME` at the deployment's `hostname`.

- **VM refunds are paid out automatically over Lightning** (issue #193) — `POST /api/admin/v1/vms/{id}/refund` no longer returns `501` for `payment_method: "lightning"`. It validates the invoice and queues the payout, answering `200` with a job id; the worker pays the invoice from the LNVPS node, records the refund against the payments it reverses, and queues the VM for deletion. **Breaking for anything that asserted on the `501`** — the request body is unchanged. The endpoint now also requires `payments::update` alongside `virtual_machines::update`: sending money out is a payments write, like recording one. **Breaking for admins holding only `virtual_machines::update`**, who now get `403`.

  The invoice must carry an amount and that amount may not exceed the pro-rated refund `GET /vms/{id}/refund` quotes (a smaller one is allowed and is what gets recorded); an invoice that does not parse, has no amount or has expired is a `400`. The worker refuses before paying when the VM's paid payments cannot absorb the refund, or when the invoice is worth less than one minor unit of the charged currency, so money never leaves with nowhere to book it. Refunds are booked newest payment first, in the currency each payment was charged in and at that payment's own frozen exchange and VAT rates, exactly as the manual `POST /vms/{id}/payments/{payment_id}/refund` records them; the Lightning preimage is stored as the refund row's `metadata.refund.external_ref`.

  `revolut` and `paypal` still return `501` — nothing here can move money through them. Issue those in the provider's dashboard and record them with the manual endpoint.

- **Referral payouts record both sides of a currency conversion** (issue #308) — a payout row now carries a **settled** side and a **sent** side. The settled side (`amount`, `fee`, `currency`) is what the payout discharges against the earned balance; commission is earned per currency and nets in the currency it was earned in. The sent side (`sent_amount`, `sent_fee`, `sent_currency`) is what actually left the wallet. `rate` is settled-currency standard units per one sent-currency standard unit, and `rate_collected` is when that rate was quoted.

  Additive on `ApiReferralPayout` (`GET /api/v1/referral`) and `AdminReferralPayoutInfo` (`GET /api/admin/v1/referrals/{id}` and `/payouts`): no existing field changes meaning. A payout that sent what it settles — every payout the automated engine makes today, and every row that existed before this change — has the two sides equal, `rate` `1` and `rate_collected` `null`. Treat a `null` `rate_collected` as "no conversion happened" rather than "rate 1 was quoted".

  `POST /api/admin/v1/referrals/{id}/payouts` accepts the sent side for reconciling an out-of-band payment: `sent_currency`, `sent_amount`, `sent_fee`, `rate`, `rate_collected`, plus `fee` on the settled side. When `sent_currency` differs from `currency`, `sent_amount` and a positive `rate` are required; when they are the same, a `rate` or a diverging `sent_amount`/`sent_fee` is rejected. Automatic conversion at send time is not implemented — a cross-currency payout is recorded by an admin today.

- **`usage` on an app deployment — what it is actually consuming** (issue #278) — `ApiAppDeployment` (`GET /api/v1/app-deployments` and `/{id}`, and every endpoint returning a deployment) gains a nullable `usage` object. Additive: no existing field changes.

  ```json
  "usage": { "cpu_milli": 250, "memory_bytes": 2097152, "storage_bytes": 8192, "collected": "2026-07-28T11:00:00Z" }
  ```

  Same units as the `cpu_milli` / `memory_bytes` / `storage_bytes` quota fields on the same object, which already have the `resource_multiplier` applied — so the two divide directly and the customer can see whether they are outgrowing their size.

  `usage` is `null` when nothing has been observed: a deployment that has never run, or a cluster whose operator has no Prometheus configured. `storage_bytes` is independently `null` for a deployment with no volumes, or when the metrics source carries no kubelet volume statistics; `cpu_milli` and `memory_bytes` are still reported in that case. Render an absent reading as unknown, not as zero — zero reads as an idle workload, which is a different claim from an unmeasured one.

  It is a sample, not a live figure: the operator writes it on its reconcile pass (60s by default) with CPU averaged over a 5-minute window, so `collected` can be minutes old. Show the age alongside it.

- **`usage.services[]` and `usage.volumes[]` — which service and which volume** (issue #305) — the `usage` object above gains two arrays, on both the customer response (`ApiAppDeployment`) and the admin one (`GET /api/admin/v1/app-deployments`, `/{id}`, `PATCH /{id}`). Additive: no existing field changes.

  ```json
  "usage": {
    "cpu_milli": 300, "memory_bytes": 3072, "storage_bytes": 5120,
    "collected": "2026-07-28T11:00:00Z",
    "services": [ { "service": "web", "cpu_milli": 100, "memory_bytes": 1024 } ],
    "volumes":  [ { "service": "web", "name": "data", "storage_bytes": 1024 } ]
  }
  ```

  The totals are namespace sums, and Kubernetes enforces CPU and memory per container and volume size per PVC — so a deployment at 40% of its total can have one container OOM-killing, or one full volume while the others are empty. The totals cannot express either; the breakdown names the service and the volume.

  Keys are the compose names the rest of the API already uses: `service` matches `services[].name` on the catalog app, and `(service, name)` matches `volumes[]` there — a volume name is only unique within its service, so the pair is the identity. Ordering is by service, then volume name.

  Both arrays are **empty, never null**, and empty is not an error: a reading taken before per-service series were collected has totals and no parts, and a series with no matching compose entry (an init container, or a volume since removed from the app) is dropped rather than reported under a name the customer cannot find. The parts are rounded individually while the totals are rounded once after summing, so a breakdown can be a millicore or two above the total it sits beside — render the total as the figure of record.

- **`usage` on the admin deployment response** (issue #304) — `AdminAppDeploymentInfo` now carries the same nullable `usage` object as the customer response, on the listing, the single `GET` and the `PATCH` response. Same units, same null semantics. Support could previously not see numbers the customer could, on the endpoint whose purpose is oversight.

- **`billing_state` on an app deployment — `unpaid` / `active` / `expired`** (issue #253) — `ApiAppDeployment` (`GET /api/v1/app-deployments` and `/{id}`, and every endpoint returning a deployment) gains a nullable `billing_state` string. Additive: no existing field changes.

  A client could not previously tell "never paid for" from "the customer stopped it". The only signals were `status` and a prose `status_message`, and the operator writes a never-paid deployment back as `stopped` with `"subscription not yet paid"` — so inferring "unpaid" from `status == "pending"` works exactly until the first reconcile, after which the page stops asking for the first payment and offers a **Start** button that the billing gate refuses. `unpaid` asks for a first payment, `expired` (paid, then lapsed; data retained at 0 replicas) asks for a renewal, and neither is a stopped app.

  It is derived from the deployment's own subscription — `is_setup`, then `expires` — by the same function the operator's run gate uses, so the two cannot disagree. `null` **only** when the subscription cannot be resolved at all, which is the same condition that already leaves `subscription_id` null: an operational fault, reported as unknown rather than as a billing verdict. Do not parse `status_message` for this; it is untranslated prose and rewording it would break the page.

- **App compose grammar: `scratch:` — writable paths a service does not keep** (issue #264) — every managed-app container runs with `readOnlyRootFilesystem`, so before this the only writable paths were the declared `volumes`. That is right for app data and wrong for the runtime directory a database image needs on the way up: `mariadb` writes InnoDB's temporary files under `/tmp` and its pid file and socket under `/run/mysqld`, `postgres` its lock and socket under `/var/run/postgresql`. With nowhere to write either, the process exits during startup — **no database image in the catalog could start**, whatever `user:` it declared. A service (and the `init:` steps that share its mounts) may now declare `scratch: [{ path, size }]`, each rendering one `emptyDir`: created empty with the pod, discarded with it. `size` defaults to `256Mi` and is capped at `1Gi`, enforced as the volume's `sizeLimit` so one tenant's scratch cannot fill the node it shares. A scratch path that sits inside a data volume — or a data volume inside a scratch path — is rejected at validation, since either would hand the customer an empty directory where their data was.

  Scratch is **not storage**: it is excluded from `footprint().storage_bytes`, from the per-volume breakdown on `GET /api/v1/apps` (issue #260) and from cluster capacity accounting, so nothing a buyer is shown or billed for changes. Existing app definitions are unaffected — the field defaults to empty. The documented `route96` and `buzz-relay` examples now declare the scratch their database services need; buzz-relay's `postgres` gets it *instead of* the 1 GiB PVC it used to mount at `/var/run/postgresql`, which drops that app's advertised storage from 21 GiB to 20 GiB when the catalog row is updated to match.

### Fixed

- **Managed app deployments — `user: root` services now keep the capabilities a root entrypoint needs** (issue #263) — `user: root` (added in #256) made the kubelet admit these containers but not work: the per-container security context dropped **ALL** capabilities for every service, so a `mariadb` service started as uid 0 with an empty capability set and its entrypoint died on `error: failed switching to 'mysql': operation not permitted` (the `su-exec` drop to its own service account, before it ever reached the `chown` of the data directory). A container that starts and then crash-loops reads as an app bug rather than a platform one. Services (and `init:` steps) that declare `user: root` now get `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID` and `SETUID` added back on top of `drop: ALL` — the chown of a freshly provisioned data directory, plus the `gosu`/`su-exec` drop to the service account that follows it. All five are permitted by the baseline Pod Security Standard, which a deployment containing a root service already runs under; `allowPrivilegeEscalation: false` and the read-only root filesystem are unchanged, and non-root services keep `drop: ALL` with nothing added, as the restricted standard requires. Affects `route96` and `buzz-relay` in the catalog. **This does not by itself get either app running:** verified against `mariadb:11` and `postgres:17`, a database service then fails on the read-only root filesystem, which leaves it no writable `/tmp` or runtime directory (issue #264). No customer-facing request/response schema change.

- **Unpaid app deployments are no longer provisioned, and no longer consume cluster capacity** (issue #252) — payment gated the replica count and nothing else, so a never-paid order still got its namespace, its generated secrets, its PVCs at full size × `resource_multiplier`, and an Ingress with a real `letsencrypt-prod` issuer on the next reconcile. Certificates are rate-limited per registered domain, so free orders could exhaust the quota for the apps domain and **deny certificates to customers who had paid**. The operator now decides the billing gate before it creates anything and returns immediately for a never-paid deployment, writing back the same `stopped` status and "subscription not yet paid" reason it always did.

  `GET /api/v1/apps/{id}/regions` and app-deployment ordering also stop counting never-paid deployments against a cluster's capacity, matching what the VM path already does. Nostr keys are free, so anyone could previously fill a cluster with unpaid orders and make a paying customer's order fail with "No cluster with enough capacity"; `available` on that endpoint now reflects paid usage. **Expired deployments still count and still keep their objects** — they were paid for, their PVCs hold customer data, and they are retained at 0 replicas until real deletion. No response shapes change.

- **Admin VM refund: `POST /api/admin/v1/vms/{id}/refund` now answers `501` instead of reporting success** (issue #193) — **breaking for admin clients that treated `200` as "refund dispatched".** The endpoint queued a `ProcessVmRefund` work job and returned `200` with its stream id, while the only handler for that job is `bail!("Refund processing is not yet implemented")`. The failure happened in a background job *after* the response, so an operator opened the refund modal, saw a genuine pro-rated amount from `GET /api/admin/v1/vms/{id}/refund`, submitted it, and was told the job had been dispatched — with no money moved, no record written and no way for either side to tell a refund from a no-op. The endpoint now refuses with `501` and a message naming the state; nothing is queued.

  The request body is still validated ahead of the refusal, so an invalid `payment_method`, or a `lightning` refund with no invoice, is still a `400`, and the permission check still runs first, so a caller without `virtual_machines::update` still gets `403`. Body and permission are unchanged, and the `ProcessVmRefund` job type is retained for the payout implementation. Recording a refund for accounting, and paying one out, are the next two parts of #193.

- **Admin app/cluster delete: soft-deleted deployments now block the delete with a `400`, not a `500`** (issue #238) — `DELETE /api/admin/v1/apps/{id}` and `DELETE /api/admin/v1/app_clusters/{id}` guarded on the *live* deployment list, but `fk_app_deployment_app` and `fk_app_deployment_cluster` do not look at `deleted`. Deployment deletion is a soft delete, so an app or cluster whose deployments were all soft-deleted passed the guard, reached the `DELETE`, and failed on the foreign key — surfacing as a `500` with a raw MySQL error. The guard now counts every deployment row that references the resource, deleted or not, so the refusal is the `400` it was always meant to be. The message reports both counts (`2 active, 3 soft-deleted`) and, when only soft-deleted rows remain, names the way out: purge them with `DELETE /api/admin/v1/app-deployments/{id}` and `{"purge": true}` (`super_admin` only), then retry the delete. Admin clients that inspect these rows need `include_deleted=true` on `GET /api/admin/v1/app-deployments` — soft-deleted deployments are hidden by default, so a refused admin otherwise sees an empty list. No response-shape change; only the error status and message for this case.

- **App compose: undeclared `${...}` references rejected at admission, tolerated at reconcile** — creating or updating a catalog app (`POST`/`PATCH /api/admin/v1/apps`) now rejects a compose that references a variable which is not declared as a `config:` field, a `secrets:` entry, or the built-in `HOSTNAME`. Previously such a compose passed validation, and the failure only appeared later when the operator tried to render a deployment. Conversely, the operator no longer fails a reconcile when a *declared* value is absent from a deployment's stored config — which happens legitimately whenever an app's compose gains a new field after that deployment was created. It now resolves to the field's `default`, or an empty string if it has none, and logs a warning, so a compose change can be rolled out without taking already-deployed instances offline. Give any newly added field a sensible `default` if a blank would break the app.

- **Invoice HTML for non-VM subscriptions** — `GET /api/v1/payment/{id}/invoice` failed with `VM not found` for any subscription that isn't a VPS (managed app, IP range, ASN sponsoring, DNS hosting). The handler resolved the payer, the selling company and the invoice line from `get_vm_by_subscription`, which matches only `SubscriptionType::Vps`. The invoice is now scoped to the subscription: ownership comes from `subscription.user_id`, the company from `subscription.company_id` (the same company the payment's tax was frozen against), and the Description cell renders one line per subscription line item regardless of type — VPS lines keep the existing `VM Renewal #id - template - distro version` label, other types use the line item's name/description. Mixed subscriptions list every line. Amount, VAT and total presentation are unchanged.

- **Lightning/on-chain invoices for app-only subscriptions** — generating a payment for a subscription with only non-VM line items (e.g. a managed app) priced in fiat failed with `Lightning payment must be in BTC` (and the on-chain equivalent). The non-VM cost was already converted to the payment method's currency, but the payment currency was only inferred from VM items, so an app-only subscription wrongly kept its fiat currency. The converted currency is now used, so fiat-priced apps can be paid via Lightning/on-chain. Also wires the `SubscriptionType::App` lifecycle handler (missing handler previously skipped expiry/grace-period cleanup of the deployment's namespace and volumes).

### Changed

- **Reports net refunds off earnings, and their totals are now signed** (issue #193) — **breaking response-shape change for admin report clients.** `GET /api/admin/v1/reports/profit-loss` returns `revenue_net`/`revenue_tax` as signed integers, and `GET /api/admin/v1/reports/oss` returns `net_total`/`tax_total` as signed integers; a period that refunds more than it sells now reports negative revenue instead of an impossible unsigned total. Refund rows subtract in both, in the period the money actually went out, and an OSS refund nets against exactly the country/rate bucket that declared the VAT because it carries that payment's frozen country, rate and treatment. `transaction_count` counts refunds too.

  `GET /api/admin/v1/reports/time-series` gains `payment_type` (`"purchase" | "renewal" | "upgrade" | "refund"`) and `refunded_payment_id` on each row. That feed is raw payment rows aggregated client-side, so a client that does not subtract `refund` rows will overstate revenue — the type is now on the row so it can.

  `AdminVmPaymentInfo` (VM payment endpoints) likewise gains `payment_type` and `refunded_payment_id`, and the customer-facing `ApiVmPayment` gains `is_refund`, so neither surface can mistake a refund for money the customer paid. `ApiVmPayment` for a refund carries an empty `data` (there is no invoice to pay); previously an unparseable payment row of this shape would have failed the whole payment list.

- **Admin app listings are paginated and filterable** (issue #235) — **breaking response-shape change for admin clients.** `GET /api/admin/v1/apps`, `GET /api/admin/v1/app_clusters` and `GET /api/admin/v1/app-deployments` previously returned every row as a bare `{ "data": [...] }` with no query parameters at all. They now accept `limit`/`offset` (default 50, max 100) and return the standard `ApiPaginatedData` envelope (`{ data, total, limit, offset }`) used by every other admin list endpoint, so the admin dashboard's shared paginated table can drive them and report a total. Results are ordered `id DESC`.

  Filters are pushed down into SQL rather than applied in the handler. Deployments accept `user_id`, `app_id`, `cluster_id`, `region_id` (matches any cluster in the region), `status`, `desired_state`, `search` (substring on `name`/`hostname`/`custom_domain`) and `include_deleted`; apps accept `enabled` and `search` (`name`/`display_name`/`description`); clusters accept `enabled`, `region_id` and `search` (`name`/`ingress_domain`). All combine with AND.

  Because deployment deletion is a soft delete, a deleted deployment was previously invisible to admins entirely — `include_deleted=true` (default `false`) is now the way to inspect a customer's torn-down deployment or confirm a teardown happened, and `AdminAppDeploymentInfo` gains a `deleted` boolean. `app` and `app_cluster` have no soft-delete, so `include_deleted` does not apply to those two — `enabled` is their only visibility filter.

- **App catalog is now public** (issue #227) — `GET /api/v1/apps`, `GET /api/v1/apps/{id}` and `GET /api/v1/apps/{id}/regions` no longer require `Nip98Auth`, mirroring `GET /api/v1/vm/templates`. The catalog is a shopping/marketing surface, so anonymous visitors and SSR homepages can browse offered apps (and per-region availability) without logging in. All user-owned deployment endpoints (`/api/v1/app-deployments...`) remain authenticated.

### Added

- **Per-volume storage breakdown on the apps catalog** (issue #260) — `GET /api/v1/apps` and `GET /api/v1/apps/{id}` gain `volumes[]`: `{ service, name, label, size_bytes }` per persistent volume, summing to the `storage_bytes` already reported. Additive; no existing field changes.

  `storage_bytes` alone misreports any app that stores more than one kind of thing. HAVEN's 30 GB is 10 GB of events and 20 GB of media, and rendered next to event-only relays quoting 10 GB it reads as three times the event storage a buyer actually gets. Clients cannot fix this themselves: volume names carry no meaning that generalises — `db` is HAVEN's event store and route96's MySQL, `data` is Pyramid's events and Buzz's Postgres, and Buzz declares two volumes both named `data` — so any client-side name table is correct for today's catalog and wrong for the next app. The purpose is therefore authored per app in the compose (`volumes: - { name: db, path: /app/db, size: 10Gi, label: events }`) and surfaced here.

  `label` is optional and nullable: a volume nobody shops for (a socket dir, a pack cache) simply has none, and an app that labels nothing yields a list a client can ignore in favour of the total — so no catalog entry has to be backfilled for this to ship. Labels are validated at authoring time (`POST`/`PATCH /api/admin/v1/apps`, and `compose-validate`): non-empty, at most 40 characters, trimmed. Ordering is by service name then declaration order, and there is deliberately **no** "primary volume" flag — both consumers render every labelled volume, so a second mechanism for "the main one" would be guessing at intent that the label already carries.

- **Refunds can be represented in accounting** (issue #193, part 2) — `SubscriptionPaymentType` had `Purchase`/`Renewal`/`Upgrade` and nothing else, so a refund could not be recorded at all: an operator who returned money to a customer by hand had nowhere to put it, and every earnings figure counted that money as revenue forever. There is now a `Refund` payment type, a `subscription_payment.refunded_payment_id` link column (migration `20260727120000_subscription_payment_refunds.sql`), and two admin endpoints on the payment being reversed:

  - `POST /api/admin/v1/vms/{vm_id}/payments/{payment_id}/refund` (`payments::update`) records a refund that has **already been paid out by hand** and returns the resulting `AdminVmPaymentInfo`. Body is all-optional: `amount` (defaults to everything still refundable), `reason`, `external_ref` (preimage / processor refund id / bank reference), `refunded_at` (defaults to now — this is the period the refund lands in, so backdating is deliberate).
  - `GET .../refund` (`payments::view`) returns the refunds recorded against a payment with `refunded_total` and `refundable_remaining`.

  The refund row is a copy of the payment it reverses, not a fresh calculation: same currency, same frozen exchange `rate`, same VAT rate, country and treatment, with `amount`/`tax` pro-rated and the tax rounded **down** so repeated partial refunds can never return more VAT than was collected. VAT is owed on what was charged, so reversing at today's rates would misstate the return — note that `GET /api/admin/v1/vms/{id}/refund` computes its number from the *cost plan at a live rate with no tax*, which is why the recorded amount is derived from the payment instead. `time_value` is null (a refund extends nothing), `processing_fee` is `0` (processors keep their fee), and a VM history entry (`refunded`) is written alongside. Partial refunds are allowed up to what is left; over-refunding, refunding an unpaid payment, refunding a refund, and resubmitting an identical refund are all refused, the last as a `409` because the row id is derived from `(payment, amount, timestamp, admin)` rather than random.

  **Amounts stay unsigned:** `amount`/`tax` hold the magnitude returned and the sign lives in the payment type, so no existing row, column or INSERT changes meaning. Every aggregation over payments must branch on the type — see the report changes below.

  Recording a refund deliberately does **not** delete or stop the VM; that stays the explicit `DELETE /api/admin/v1/vms/{id}`, so an accounting correction cannot destroy a customer's machine as a side effect. Paying a refund out automatically is still unimplemented (part 3): `POST /api/admin/v1/vms/{id}/refund` continues to answer `501`.

- **App compose: a service can declare `init:` setup steps that must succeed before it starts** (issue #244) — a compose `service:` was `image` + `env` + `ports` + `volumes` + `files`; there was no `command` and no init hook, so a deployment could not perform a setup step the image does not do on its own entrypoint. Object storage is the case that broke on it: an S3 server starts empty, and a consumer that expects its bucket to exist dies on `NoSuchBucket` (the Buzz relay's startup object-store probe does exactly this). A service may now declare `init: [{ name, image, command, args, env, resources, user }]`, rendered as Kubernetes init containers in that service's own pod: they run to completion in declaration order, the kubelet restarts a failed one and does not start the service's container until they have all exited 0. That is also the gate — a service whose setup has not succeeded never runs. A step that prepares a *peer* service belongs on the consumer, not the peer: a bucket cannot be created in a server that has not started, and it is the consumer that must not run without it.

  A step sees exactly what the service's container sees (its `volumes` and `files`, at the same paths) plus a writable `/tmp`, runs under the same non-root hardening, and inherits the service's `user:` unless it names its own. `resources:` defaults to `50m`/`64Mi`; a pod reserves `max(largest init container, sum of containers)`, so a small step adds nothing to the app's capacity footprint and a larger one raises it. Validated at authoring time (`POST`/`PATCH /api/admin/v1/apps`, and `compose-validate`): the name must be a unique DNS label (it becomes a container name), the image is required, and **`${…}` is rejected in `command`/`args`** — a customer-supplied `config` value interpolated into a shell string is an injection, so values go through the step's `env`, where `${…}` resolves as everywhere else. Existing composes are unaffected: `init` is optional and absent everywhere in the catalog today.

- **App compose: a generated secret can declare its byte length** (issue #243) — `secrets: - { name: X, generate: password|token }` always produced 24 random bytes hex-encoded (48 characters), whatever the `generate` variant. That is fine for a database password and unusable for anything that must be a key of an exact size: the Buzz relay's `BUZZ_RELAY_PRIVATE_KEY` is a 32-byte Nostr secret key and exits at startup with `invalid BUZZ_RELAY_PRIVATE_KEY: Invalid secret key` on any other width. The declaration now takes an optional `bytes:` (`- { name: RELAY_PRIVATE_KEY, generate: token, bytes: 32 }` → 64 hex characters), validated to `16..=64` when an app is created or updated (`POST`/`PATCH /api/admin/v1/apps`, and `compose-validate`) so a typo'd length is rejected at authoring time rather than becoming a crash loop. `bytes` defaults to 24, so every existing catalog compose is unaffected, and generated secrets are still only created when absent, so existing deployments keep their stored values even if a declaration's length changes. The alternative was declaring the key as a customer-filled `config:` field, which put an app's long-lived identity key in the order form; that workaround is now gone from the documented Buzz example.

- **App catalog tags — many-to-many grouping labels, with a filter and a facet endpoint** (issue #240) — the second axis to `category`, which `category`'s own doc-comment recorded as a known trade-off: its values are specific enough to build a page title from (`Community Nostr relay`) and therefore do not group, so a "show me all relays" facet needed something coarser. **`category` is unchanged and still required** — the two answer different questions and neither replaces the other. A coarser *column* was the wrong shape, because route96 is legitimately both a media server and a Nostr thing; the grouping axis is many-to-many.

  Two new tables (`app_tag`, `app_tag_assignment`, cascading on both sides) and a seeded vocabulary of five: `nostr`, `relay`, `media-server`, `blossom`, `nip-96`. The vocabulary is **controlled** — assigning an unknown slug is a `400` naming it, never an implicit create, because auto-creation is precisely the drift (`Nostr relay` / `nostr-relay` / `nostr` as three tags) that a real table exists to prevent.

  **Public.** `ApiApp` gains `tags: [{ slug, display_name }]`, ordered by slug and possibly empty — an untagged app is a normal state. Both fields are sent, not the bare slug: a client cannot recover `NIP-96` from `nip-96`, and title-casing it in JS mangles exactly the protocol names that make good tags.

  `GET /api/v1/apps` gains a repeatable **`?tag=<slug>`** filter combining with **AND** (`?tag=nostr&tag=relay` returns apps carrying both); `?tag=nostr,relay` is accepted as an equivalent spelling. An unknown or retired slug yields an empty list with `200`, not `404` — the caller is a filter UI, and a stale chip should degrade to "no results", not an error page. `?tag=` with no value means "no filter". `GET /api/v1/apps/{id}` is unchanged apart from the new field.

  New **`GET /api/v1/app-tags`** (public, like the catalog) returns `[{ slug, display_name, description, app_count }]`, where `app_count` counts **enabled** apps only. It exists as its own endpoint so a facet bar can be sized — and a one-app tag suppressed from getting its own landing page — without fetching the whole catalog to derive the counts client-side.

  **Admin.** All of it reuses `AdminResource::App`: no new enum value, **no RBAC migration**, and nothing to grant to existing app-admin roles. `AdminAppInfo` gains `tags`, and `POST`/`PATCH /api/admin/v1/apps` take `tags: string[]` with **replace-set** semantics — omit to leave the set unchanged, `[]` to clear, a list to make that list exact. A repeated slug is one assignment. An unknown slug fails the whole request before any write, so a rejected create leaves no app behind and a rejected patch leaves the existing tags untouched. New `GET`/`POST /api/admin/v1/app-tags` and `GET`/`PATCH`/`DELETE /api/admin/v1/app-tags/{id}` manage the vocabulary; the delete cascades assignments and reports `assignments_removed`, because that untagging is otherwise invisible to the admin who caused it.

- **App catalog metadata: `category`, `seo_title`, `seo_description`** (issue #239) — **breaking for admin clients that create apps.** The catalog carried nothing describing *what class of software* an app is, so the public app page's title copy was a hardcoded per-slug map in the frontend: adding an app in admin produced a live page with its card blurb for a title, and nothing errored. `App` now carries the missing field, and all three appear on `ApiApp` (`GET /api/v1/apps`, `GET /api/v1/apps/{id}`) and `AdminAppInfo`.

  `category` is a **required, non-null, free-text** string — the shortest phrase that is true of this app and not of its neighbour (`Nostr relay`, `Blossom media server`, `Community Nostr relay`). Clients template around it, e.g. `{display_name} Hosting — Managed {category}`; it is also suitable for `Product.category` in structured data. Free text rather than an enum so onboarding a new class of app does not need a migration. Format contract, unrepairable downstream because the stored string is what search engines show: sentence case with proper nouns capitalised, no article, no "hosting"/"managed", no trailing punctuation. Known trade-off, accepted: values this specific do not group, so a future "all relays" facet needs a second, coarser column.

  `seo_title` / `seo_description` are **nullable per-app overrides** for when the template is not good enough, and are null for almost every app. They arrive over the wire, so they are never picked up by a client's message extraction — an English-only escape hatch, with `category` carrying the localisable general case.

  **Admin write surface.** `POST /api/admin/v1/apps` now **requires** `category` (omitted → `422`; blank or whitespace-only → `400 category is required`); it is stored trimmed. On `PATCH /api/admin/v1/apps/{id}`, omitting `category` leaves it unchanged and an explicit `"category": null` is **refused with `400`** rather than silently ignored — there is no null to clear to on a `NOT NULL` column, and the two nullable overrides do accept `null` to clear. Now is the cheap moment to make it required: `LNVPS/web` only ever reads the catalog and `LNVPS/admin` has no managed-apps surface yet, so no existing client creates apps.

  The migration adds the three columns nullable, backfills the five catalog apps with reviewed copy (any other row gets the placeholder `Self-hosted application`), then sets `category NOT NULL`.

- **Admin delete & purge for app deployments and subscriptions** (issue #234) — there was previously no way for an admin to remove an app deployment at all, and no way to remove a subscription that had ever been paid, so test/demo data and orphaned billing rows accumulated permanently.

  New `DELETE /api/admin/v1/app-deployments/{id}` (`app_deployment::delete`) is the admin equivalent of the customer delete: it deactivates billing and soft-deletes the deployment, and the operator tears down the namespace and its volumes on the next reconcile. Following the VM rule, a deployment whose **first payment was never confirmed** carries no billing history and is removed entirely instead. An optional `{ "purge": true }` body hard-deletes the `app_deployment` row together with its `subscription`, `subscription_line_item` and payment rows in one transaction; it requires the `super_admin` role (`403` for everyone else, checked before the lookup, exactly like the VM purge). An already soft-deleted deployment can still be purged; a plain delete of one returns `409`. Purging does not orphan Kubernetes resources — the operator garbage-collects any `app-{id}` namespace whose deployment is absent from its active set, and a purged row is absent exactly like a soft-deleted one.

  `DELETE /api/admin/v1/subscriptions/{id}` gains the same optional `{ "purge": true }` body, again `super_admin`-only: it bypasses the "N paid payments exist" guard and cascades line items and payments. It is refused while a VM or app deployment still references one of the subscription's line items — those resources must be deleted first. Regular deletes keep today's guard and behaviour unchanged.

  No migration is needed: the `app_deployment` permission set (including `delete`) was already seeded for `super_admin`.

- **Managed app deployments — resource upgrades** — a deployment now carries a `resource_multiplier`: its size as a multiple of the catalog app's base footprint *and* price (`1` = the base app, which is what every existing deployment is). The operator multiplies every container's CPU/memory limits and every PVC's size by it, cluster capacity accounting counts the multiplied footprint, and the subscription line item is priced at `app.amount x resource_multiplier`.

  Two new endpoints: `POST /api/v1/app-deployments/{id}/upgrade-quote` returns the prorated cost of resizing (`cost_difference`, `new_renewal_cost`, `discount`, `tax`, `processing_fee`) without charging anything, and `POST /api/v1/app-deployments/{id}/upgrade` creates the upgrade payment and returns an `ApiSubscriptionPayment`. Both take `{ "resource_multiplier": N }` and accept the usual `?method=` / saved-payment-method query. Pricing mirrors VM upgrades: you pay the new rate for the time remaining on the current period, minus a credit for that time already bought at the old rate; the expiry is unchanged because an upgrade buys capacity, not time.

  The resize is applied **only when the payment settles**, so an abandoned upgrade leaves the deployment untouched. Upgrades are **increase-only** (a PersistentVolumeClaim cannot shrink, so a downgrade would strand storage) and capped at 16x; the *additional* footprint must fit on the cluster the deployment already runs on, since its volumes live there and it cannot be moved. `GET /api/v1/app-deployments` and `/app-deployments/{id}` now return `resource_multiplier` plus the effective `cpu_milli` / `memory_bytes` / `storage_bytes` after applying it, and the admin `AdminAppDeploymentInfo` exposes `resource_multiplier` read-only. A migration adds `app_deployment.resource_multiplier` (`NOT NULL DEFAULT 1`).

  Note for operators: growing a PVC requires a StorageClass with `allowVolumeExpansion: true`. Without it the pod specs scale but the volumes will not, and the deployment will report a failed expansion.

- **Single subscription payment lookup** — new `GET /api/v1/subscriptions/{id}/payments/{payment_id}` returns one `ApiSubscriptionPayment`, for any subscription type. This is the item form of the existing payments list, for polling a single payment (e.g. a checkout awaiting settlement) without fetching the whole history — the replacement for the deprecated VM-only `GET /api/v1/payment/{id}`. The subscription id is always available to callers because it is returned on the payment object itself (`subscription_id`). Ownership is enforced on the subscription (`403`); because payment ids are globally unique, a payment that exists but belongs to a different subscription than the one in the path returns `404` rather than confirming its existence.

- **Managed app deployments — custom domains** — `PATCH /api/v1/app-deployments/{id}` now accepts `custom_domain` (a customer-owned hostname, e.g. `blog.example.com`; `""`/`null` clears it), and `GET /api/v1/app-deployments` + `/app-deployments/{id}` return it. The customer points a CNAME at the deployment's `hostname`; the operator then serves the custom domain alongside the default `{name}.{ingress_domain}` host on the same Ingress and cert-manager issues a separate TLS certificate for it (HTTP-01) once DNS resolves (stored in the `app-tls-custom` secret, distinct from the default `app-tls`). No pre-verification — certificate issuance itself only succeeds when the DNS points at the cluster. Also exposed on the admin `AdminAppDeploymentInfo`. A migration adds the nullable `app_deployment.custom_domain` column.
- **Managed app deployments — admin read/write of name, custom domain & config** — new admin endpoints under a dedicated `app_deployment` RBAC resource (distinct from the catalog `app` resource): `GET /api/admin/v1/app-deployments/{id}` (`app_deployment::view`) returns a single deployment including its decrypted `config` map (may hold secret values — admin-only), and `PATCH /api/admin/v1/app-deployments/{id}` (`app_deployment::update`) updates `name` (DNS-safe, unique per cluster), `custom_domain` (validated; `""`/`null` clears) and/or `config` (validated against the compose schema), mirroring the customer PATCH for support/ops fixes. The existing list endpoint `GET /api/admin/v1/app-deployments` now requires `app_deployment::view` (was catalog `app::view`) and still excludes config. The name/config/custom-domain validation is shared between the customer and admin APIs via the `lnvps_compose` crate. A migration seeds the `app_deployment` permission set for `super_admin`.
- **Managed app deployments — per-service `user: root` opt-out** — the app `compose` grammar gains an optional per-service `user` field. When a curated catalog service sets `user: root` (or `0`), the operator sets that container's `runAsNonRoot: false` and drops the deployment namespace to the baseline Pod Security Standard, so images whose entrypoint must *start* as root and drop privileges themselves (e.g. `mariadb`, `postgres`, `redis`) can run. All other hardening (no privilege escalation, drop ALL capabilities, read-only root filesystem) still applies; services without `user:` keep the default restricted PSS + `runAsNonRoot`. No customer-facing request/response schema change.
- **Managed app deployments — edit (rename / reconfigure)** — new `PATCH /api/v1/app-deployments/{id}` updates a deployment's `name` and/or `config` (partial; only fields present change). Renaming is validated DNS-safe and checked unique on the cluster (the name is the ingress hostname subdomain); `config` is validated against the app's compose schema and replaces the stored config wholesale. Only the app's declared `config:` fields can be set — the compose (image, resources, volumes, ports) stays fixed by the catalog. The operator re-applies the change on its next reconcile.
- **Managed app deployments — current config on the deployment** (issue #232) — `GET /api/v1/app-deployments` and `/app-deployments/{id}` now return the deployment's current customer-supplied `config` map (decrypted for the owner; generated `secrets:` are never exposed), so the edit form can prefill and a config `PATCH` preserves untouched fields.
- **Managed app deployments — resource footprint on the customer App** (issue #231) — `GET /api/v1/apps` and `/apps/{id}` now expose the app's resource footprint computed from the compose: flat totals `cpu_milli` / `memory_bytes` / `storage_bytes`, plus a per-service breakdown `services[] = { name, cpu_milli, memory_bytes, storage_bytes }` (sorted by name, summing to the totals). Lets the catalog/detail pages show what each container in a multi-service app uses without recomputing from the compose client-side. Read-only, additive.

- **Managed app deployments — admin listing** — new `GET /api/admin/v1/app-deployments` (permission `app::view`) lists every non-deleted deployment across all users and clusters for oversight/support (`AdminAppDeploymentInfo`; excludes the encrypted config blob).
- **Exchange-rate feed** (issue #230) — new public, cacheable endpoint `GET /api/v1/exchange-rate` exposes the rates the pricing engine maintains (BTC spot + fiat↔fiat FX). Returns `{ updated, base, rates }` where `1` unit of `base` (default `BTC`, override with `?base=EUR`) equals `rates[X]` units of currency `X` in standard units; the base itself is excluded. Clients derive any pair as `rates[B] / rates[A]`, letting them reconcile a payment method's `min_amount` (quoted in its own currency) against an order priced in a different currency, and render cross-currency figures where `other_price[]` isn't provided (e.g. subscriptions). Read-only, additive.

- **Managed app deployments — operator reconcile** (part of the App Deployments epic) — the `lnvps_operator` now reconciles `app_deployment` rows for its configured cluster into Kubernetes: one locked-down namespace per deployment (restricted Pod Security + default-deny NetworkPolicy), a Deployment + ClusterIP Service per compose service, a cert-manager-TLS Ingress for the `expose: ingress` port, PVCs for `volumes:`, and ConfigMap/Secret-backed `files:` mounted read-only. Generated `secrets:` are created once and kept stable; `${…}` env/files are resolved per deployment. PVCs use the cluster's default StorageClass. Retention is data-preserving: an **expired** deployment is scaled to **0 replicas** (pods stop, persistent volumes retained) rather than torn down — only real deletion removes the namespace/volumes. - **Managed app deployments — config-file mounts (`files:`)** (part of the App Deployments epic) — the app `compose` grammar now supports injecting read-only config files into a container (rendered into a ConfigMap, or a Secret when `sensitive`, and mounted via `subPath`), so file-driven apps (e.g. strfry's `strfry.conf`) are deployable. Each service's `files:` entry declares a `path` plus either inline templated `content` (with `${…}` filled from `config`/`secrets`) or `content_from` a `config` field (including a new `type: file` for customer-supplied whole files). Validated by the shared parser (and therefore the admin catalog API): absolute non-traversal paths, a single content source, ≤256 KiB inline content, `content_from` must reference a declared field, and a file may not overlap a read-write data volume. Ordering and lifecycle control land in a later increment.
- **Managed app deployments — admin catalog & clusters** (part of the App Deployments epic) — new admin endpoints to manage a catalog of predefined "apps" (e.g. Nostr relay, Blossom) deployed on shared Kubernetes infrastructure, and the clusters they run on. `GET/POST /api/admin/v1/apps` and `GET/PATCH/DELETE /api/admin/v1/apps/{id}` manage catalog apps (each defined by a docker-compose-style `compose` YAML plus subscription pricing); `GET/POST /api/admin/v1/app_clusters` and `GET/PATCH/DELETE /api/admin/v1/app_clusters/{id}` manage clusters (each bound to a `region` — which provides the billing company — and an ingress domain). Gated behind a new `app` admin permission (granted to `super_admin` by default). No customer-facing surface yet — deployment ordering and the operator reconcile land in later increments.
- **User-chosen referral payout threshold** — referrers can now set a personal `payout_threshold` (in **satoshis**) on `POST`/`PATCH /api/v1/referral`, and it's returned on the `Referral` response and admin referral endpoints. This lets a referrer (on-chain ones in particular) avoid many tiny payouts by batching commission up to a larger amount. The value must be **at least the system minimum** for the payout method (the API rejects lower values); the effective threshold used at payout time is `max(system minimum, payout_threshold)`, so a referrer can raise — but never lower — the bar. `null`/omitted uses the system minimum (unchanged behaviour). A migration adds the nullable `referral.payout_threshold` column.
- **Host CPU architecture on VM status** (issue #210) — the customer VM status (`GET /api/v1/vm/{id}` and `GET /api/v1/vms`) now includes an optional `cpu_arch` string (`"x86_64"`/`"arm64"`) sourced from the **host** the VM runs on. Unlike `template.cpu_arch` (an optional template *constraint* that is omitted when the template doesn't pin an architecture), this reflects the concrete host architecture and is present whenever it's known, so clients can always pass `?arch=` when listing OS images for a reinstall (see #202) and avoid offering images that would fail provisioning (see #183). Read-only, additive; omitted when the host arch is unknown.
- **On-chain referral payouts, batched into one transaction** (issue #184) — referrers can choose a new `on_chain` payout mode and register an on-chain Bitcoin payout address (**mainnet**; regtest also accepted in debug builds for the e2e stack). The automated worker pays **every eligible on-chain referrer in a single send-many transaction**, gated by `min-onchain-payout-sats` under `[referral]` (default 1000; `null` disables). Key behaviours:
  - **The referrer bears the network fee.** The transaction fee is split across the batch in proportion to each payout and debited from the referrer's balance alongside the amount, so a fee-induced deficit is recovered from future referrals. Lightning payouts likewise now charge the referrer the routing fee. Recorded as `ReferralPayout.fee`.
  - **Fee-rate cap.** Before broadcasting, the next-block fee rate is obtained from a configurable estimator (`fee-estimator`: mempool.space by default, or a fixed rate for regtest) and the batch is deferred if it exceeds `max-onchain-fee-per-vbyte` (default 50 sat/vByte), so payouts wait for cheaper fees.
  - **Precise outpoint.** Each on-chain payout records its exact `"{txid}:{vout}"` outpoint (rows from one batch share the txid, distinct vouts), decoded from the broadcast transaction.
  - **Unified `address` + payout `output`/`mode` fields.** The mode-specific `lightning_address` field is replaced by a single `Referral.address` (type implied by `mode`). Likewise a payout's `invoice`/`outpoint` are merged into a single `ReferralPayout.output` (a BOLT11 invoice for Lightning payouts, or the on-chain outpoint for on-chain payouts), with a new `ReferralPayout.mode` recording how it was paid so `output` can be interpreted without joining to the referral. Exposed on `POST`/`PATCH /api/v1/referral` (accept `address` + `mode: "on_chain"`), the `Referral`/`ReferralPayout` responses (`address`, `mode`, `output`, `fee`), and the admin referral endpoints. Migrations rename `referral.lightning_address` → `address` and `referral_payout.invoice` → `output`, and add `referral_payout.mode` + `fee`. Requires `payments-rs` 0.7.0 (`OnChainProvider::send_coins` returns the raw transaction).
- **Filter OS image listing by CPU architecture** (issue #202) — `GET /api/v1/image` now accepts an optional `?arch=` query param (`x86_64`/`amd64`, `arm64`/`aarch64`). When set, the listing returns only images of that architecture plus architecture-agnostic images, so clients can avoid offering incompatible images in the order UI. An unrecognised value returns `400`. Omitting the param is unchanged (returns all enabled images). Follow-up to #183.
- **Configurable Proxmox memory-ballooning floor** (issue #196) — new optional `balloon-min-pct` under the Proxmox `qemu` config. When set (1..=99), created and reconfigured VMs carry a `balloon` value of `memory_mb * pct / 100`, so PVE auto-ballooning can reclaim up to the remaining `(100 - pct)%` of a VM's RAM under host memory pressure — a graceful pressure-relief valve that guards against the host OOM-killer hard-killing customer VMs at high memory load. The guest is always guaranteed at least `pct`% of its sold RAM. Unset / `0` / `>= 100` leaves the `balloon` key out (dynamic ballooning disabled — the previous behaviour). Existing VMs pick up the value on their next reconfigure. No API surface change.
- **CPU architecture on VM OS images** (issue #183) — `vm_os_image` now carries a `cpu_arch` (x86_64 / arm64), so the image catalog is no longer architecture-blind. Provisioning now rejects deploying an image whose architecture is incompatible with the chosen template's architecture (an `Unknown`/unspecified arch on either side still means "any", preserving existing behaviour). Exposed as an optional `cpu_arch` string (omitted when unspecified) on the public `GET /api/v1/image` (`VmOsImage`) and the admin VM OS image endpoints — settable on `POST /api/admin/v1/vm_os_images` (defaults to `x86_64` when omitted) and `PATCH /api/admin/v1/vm_os_images/{id}` (send `null` to reset to unspecified), and returned on the admin image info responses. A migration adds the column with a default of `x86_64`, correct for all existing images.
- **Admin VM notes** (issue #135) — VMs now carry a free-form, admin-only `admin_notes` field (not exposed to the customer API). Set/clear it via `PATCH /api/admin/v1/vms/{id}` (`admin_notes`: string to set, `null` to clear, omit to leave unchanged), and it's returned on the admin VM info responses (`GET /api/admin/v1/vms` and `GET /api/admin/v1/vms/{id}`, omitted when empty). Updating notes alone persists immediately without dispatching a host reconfigure job. A migration adds the nullable `vm.admin_notes` column.
- **Bulk-extend all active VMs** (issue #96) — new admin endpoint `POST /api/admin/v1/vms/extend-all` extends every active VM by a given number of days (1–365) in a single request, e.g. to compensate customers for downtime. "Active" means non-deleted VMs whose subscription has been set up (paid at least once) — this **includes currently-expired VMs**, so a lapsed VM can be revived; never-paid pending orders and deleted VMs are excluded at the database level (a new `list_active_vms` query) and never fetched. Each extended VM is logged to its history and re-synced via a `SpawnVm` job, identical to the single-VM `PUT /api/admin/v1/vms/{id}/extend`. Returns a summary `{ extended, failed }`. This fleet-wide action is gated behind a **new `bulk_update` admin permission** (`AdminAction::BulkUpdate`), granted only to the `super_admin` role by default — a migration adds `virtual_machines::bulk_update` to super_admin, and operators can grant it to custom roles via the roles API.
- **On-chain deposit outpoint surfaced before confirmation** — the payment `data` for an `onchain` payment now includes an `outpoint` (`"{txid}:{vout}"`) as soon as the deposit is first seen in the mempool (0-conf), before it confirms. Exposed on `GET /api/v1/payment/{id}` and `GET /api/v1/vm/{id}/renew` (VM payments) and the subscription payment endpoints. Combined with `is_paid`, clients can now distinguish *waiting for payment* (no `outpoint`), *received, waiting for confirmation* (`outpoint` set, `is_paid: false`), and *confirmed* (`is_paid: true`). Omitted until a deposit is detected.
- **Sunset a host** (issue #175) — hosts now support an optional `sunset_date`. Setting it **decommissions the host**: the host is forced `enabled = false` (so it takes no new VMs, via the existing disabled-host handling), while existing VMs keep running and can still be **renewed up to the sunset date**. Once a VM's current expiry has reached the sunset date, its renewals are rejected — users renew right up to the deadline, then must migrate to another VM. Set/clear via the admin host endpoints: `sunset_date` is accepted on `POST /api/admin/v1/hosts` and `PATCH /api/admin/v1/hosts/{id}` (send `null` to un-sunset — `enabled` is left untouched so the operator re-enables explicitly), and returned on the admin host info responses. The user-facing VM status (`GET /api/v1/vm/{id}` and `GET /api/v1/vms`) now includes a `host_sunset_date` field on VMs whose host is being sunset (omitted otherwise), so clients can warn the user to migrate before the deadline.
- **Payment method minimum amount** — payment method configs now support a `min_amount` (+ `min_amount_currency`) in smallest currency units. Payments whose gross total (net + tax + processing fee) is below the configured minimum are rejected for that method, avoiding uneconomic small charges (e.g. Revolut's flat 20c base fee dominating a tiny payment). Exposed on the public `GET /api/v1/payment/methods` and admin `vm`/payment method config endpoints (`GET/POST/PATCH /api/admin/v1/payment_method_configs`). Lightning has no minimum. Fixes #170.
- **New OS distributions** — the `OsDistribution` / `ApiOsDistribution` enum now includes `almalinux`, `rockylinux`, `alpine`, `nixos`, `openbsd`, `netbsd`, `gentoo`, and `voidlinux`. Affects `GET /api/v1/image`, VM status responses, and the admin VM OS image endpoints (`GET/POST/PATCH /api/admin/v1/vm_os_image`).

### Changed

- **On-chain deposits to non-VM subscriptions are now priced from live line-item pricing** (issue #181) — a new `PricingEngine::get_subscription_cost_by_amount` turns an arbitrary paid amount into time for any subscription, priced from its line-item amounts and billing interval (`interval_amount`/`interval_type`) with the same tax + processing-fee handling as the VM path. The on-chain payment watcher now uses it for subscriptions without a VM (IP range, DNS, ASN, …), replacing the previous fallback that scaled the payment's original (stale) quote by the value received. All on-chain deposits — VM and non-VM — are now re-generated uniformly from current pricing. No API surface change.
- **VM reinstall now runs on the worker instead of inline in the API request** — `PATCH /api/v1/vm/{id}/re-install` previously executed the stop → wipe → re-import → start pipeline directly in the HTTP handler, which could race a still-in-flight provision (spawn) of a freshly-paid VM and surface confusing errors. The reinstall is now dispatched as a worker job (serialised with spawn on the same worker), and the API waits on a pub/sub job-feedback reply before responding. On success it returns `200`; on a worker-reported failure it returns an error with the reason; if the reinstall is still running after 180s (large disk imports) it returns `200` and the job continues (VM state is refreshed by the periodic check). Deployments without a Redis feedback service fall back to running the pipeline inline as before. Up-front validation (ownership, expired-VM guard, image switch) is unchanged. No request/response schema change.
- **Payment providers are now configured exclusively in the database** (issue #182) — the Lightning node, on-chain provider and Revolut service used at startup are now constructed from the per-company `payment_method_config` rows (via `PaymentMethodFactory`). The YAML `lightning:` / `revolut:` config sections have been **removed**, along with the one-time YAML→DB seed migration and the `Settings::get_node`/`get_onchain`/`get_revolut` helpers. Providers must be configured via the admin API (`POST/PATCH /api/admin/v1/payment_method_configs`); startup now fails with a clear error if no enabled Lightning/on-chain config exists for the default company. The on-chain provider now honours the DB `min_confirmations`, `address_type` and `account` fields (previously hardcoded to 1 / p2wkh / default account). The runtime still resolves a single global provider set from the default (first) company; true per-company provider routing remains future work. **Operators must ensure their `payment_method_config` rows are seeded before upgrading** (deployments that ran the previous seed migration already are). No API surface change.
- **Custom VM price quote now returns converted prices** — `POST /api/v1/vm/custom-template/price` now returns `{ currency, amount, other_price }`, where `other_price` lists the same quote converted into the other supported currencies (matching the template listing's `cost_plan.other_price`). Previously it returned only the single base-currency `{ currency, amount }`; existing clients reading those two fields are unaffected.
- **Currency conversion (`alt_prices`) de-duplicates per target currency** — the price-conversion helper behind every `other_price` list (templates, custom pricing quote, IP-space pricing) no longer emits duplicate entries for the same currency. When both a direct fiat FX rate (e.g. `EUR/USD`) and the BTC round-trip (`EUR→BTC→USD`) exist, it now keeps a single entry and **prefers the direct fiat FX rate** (ECB is more accurate for fiat↔fiat than hopping through BTC). Single-currency deployments (no direct fiat FX rates) are unchanged.
- **Renewals are now bounded by a maximum prepay window** — a renewal is rejected (with a clear error) once it would push a subscription's expiry beyond `now + max_prepay_days`. This bounds both an oversized single `?intervals=N` request and repeated back-to-back renewals (once expiry is ~the window out, further renewals are rejected until real time passes). Affects `POST /api/v1/vm/{id}/renew` and `POST /api/v1/subscriptions/{id}/renew`. The limit is configured per company (`max_prepay_days` on `POST`/`PATCH /api/admin/v1/companies`, also returned on company info; `0` inherits the global default) with a global fallback (`max-prepay-days` in service config, default 365 days). It composes with host sunsetting — the effective ceiling is the earlier of the sunset date and the prepay window. The effective window is also surfaced to clients on the user-facing VM status (`GET /api/v1/vm/{id}` and `GET /api/v1/vms`) as `max_prepay_days`, so the UI can cap the renewal interval selector to what the server will accept.
- **Exchange module: precise conversions + fiat FX rates** — currency conversion is now integer-precise (done in `f64` on smallest-unit values instead of routing through `f32`, which previously lost a unit, e.g. €1.00 → 999,999 msat instead of 1,000,000). The exchange service now also pulls fiat FX rates (from frankfurter.app / ECB) between the distinct company billing currencies — anchored on each company's own `base_currency`, not a hardcoded base, and only when companies bill in more than one fiat currency — alongside BTC prices. The pricing engine can resolve arbitrary currency pairs directly, inverse, or via a BTC/EUR cross rate. The processing-fee base amount is now properly converted into the transaction currency instead of being used as-is.
- **OS image downloads now run in parallel across hosts** — the `DownloadOsImages` worker job previously processed hosts strictly sequentially (each host waited for the previous host to finish all images). Hosts are now processed concurrently; images on a single host remain sequential to avoid saturating that host's storage backend. Affects the admin `POST /api/admin/v1/vm_os_images/{id}/download` endpoint and the periodic image check.
- **DNS is now best-effort during VM provisioning** — forward (A/AAAA) and reverse (PTR) DNS records are convenience only and no longer block or roll back a deploy. Previously a reverse-DNS failure (notably OVH rejecting a PTR with a `4xx` until the forward name resolves — a fatal, non-retried error) tore down the whole pipeline and destroyed the freshly-created VM. Now such failures are logged and the deploy proceeds; the VM keeps its IPs and MAC. Any records that failed to create are reconciled automatically on the periodic VM check (and can still be forced via the existing DNS patch job).

### Fixed

- **On-chain payment method configs can now be updated** — `PATCH /api/admin/v1/payment_method_configs/{id}` with an on-chain `config` (`"type": "onchain"`) previously failed with `422 unknown variant \`onchain\``, because the admin partial-config type was missing the on-chain variant. This blocked editing an on-chain provider config at all, including setting its `min_amount`. The partial config now supports `onchain` (url, cert/macaroon paths, address type, account, min confirmations), merging only the provided fields onto the existing config; as before, the provider *type* cannot be changed on update. (Creating on-chain configs already worked.)
- **Amount→time pricing now treats the paid amount as gross (tax + fee taken out, not added on)** — the amount-based pricing (`get_cost_by_amount` for LNURL/on-chain VM top-ups, and the new `get_subscription_cost_by_amount`) previously treated the input as the **net** price and computed tax/fee *on top* of it. But the amount a customer actually pays is the **gross** total — the sats a wallet sends for an LNURL top-up, or an on-chain deposit — so tax (and any processing fee) must be taken **out** of it to get the net that buys time. Both methods now back the net out of the gross (`net = (gross·(1 − fee_rate) − fee_base) / (1 + tax)`, via a new `PricingEngine::net_from_gross`) and the returned `amount`/`tax`/`processing_fee` sum to exactly the paid amount. Practical effects: an LNURL top-up for a taxed customer now buys time worth the net (previously the full amount was treated as net, over-crediting time and generating an invoice larger than requested); on-chain deposits now also remove the processing fee, not just the tax. No effect for untaxed, no-fee payments (net already equalled the paid amount).
- **LNURL-pay callback no longer emits a non-spec `hodl_invoice` field** (issue #197) — `GET /api/v1/vm/{id}/renew-lnurlp` previously returned `{"pr": "...", "hodl_invoice": null}` (the extra field came from the `lnurl-rs` response type). `hodl_invoice` is not part of any LUD, and strict wallets such as LNbits (1.5.5) refused to pay the invoice because of the unexpected field. The endpoint now returns a spec-compliant LUD-06 response containing only `pr` (and an empty `routes` array); the `hodl_invoice` key is gone.
- **Reinstall no longer blocked on a VM whose expiry hasn't been set yet** — `PATCH /api/v1/vm/{id}/re-install` rejected the request with `402 "Cannot re-install an expired VM, please renew it first"` whenever the VM's subscription had no `expires` value. A null expiry is not an expired VM — it's a subscription that hasn't been given an expiry yet (e.g. a freshly provisioned VM whose payment expiry hasn't propagated), which the client already renders as *new*, not *expired*. Reinstall now only rejects a **concrete** expiry at/before now, and a missing/failed subscription lookup now surfaces as an error rather than being silently treated as expired.
- **Compressed OS images (`.xz`, `.zst`, `.gz`, `.bz2`, `.lzo`) now usable on Proxmox** — image URLs pointing at a compressed disk image previously failed: Proxmox's `download-url` API rejects compressed filenames (`.qcow2.xz` → "wrong file extension") and its own decompression is unreliable, so no VM could be provisioned from them. Proxmox OS image downloads now bypass the `download-url` API entirely and fetch the file directly on the host over SSH (`wget`/`curl`, which follow redirects natively and no longer need Proxmox's flaky redirect/checksum handling). Compressed images are then verified against their `SHASUMS` entry and decompressed on the host into the final `.img` (via `xz`/`zstd`/`gzip`/`bzip2`/`lzop`, using temp-file + atomic move so a partial download/decompression never leaves a truncated image). Supported extensions: `.xz`/`.lzma`, `.zst`/`.zstd`, `.gz`, `.bz2`, `.lzo`. Affects the admin `POST /api/admin/v1/vm_os_images/{id}/download` endpoint and the periodic image check.
- **On-chain payment config now imported on existing deployments** — the payment method config data migration skipped entirely when *any* config already existed, so deployments that had already imported their LND Lightning config never got the newer LND on-chain config seeded. The migration now checks per payment method (Lightning / OnChain / Revolut) and imports only the missing ones.
- **OS image downloads no longer stall the service** — the host image download now runs its blocking SSH work (`wget`/decompress/checksum via the `ssh2`/libssh2 binding) on the blocking thread pool instead of a tokio worker thread, and each host is downloaded on its own task. Previously a single long download (e.g. a multi-minute FreeBSD image) blocked the async runtime, serialising all hosts and timing out unrelated work (other hosts' Proxmox API calls, nostr, Telegram). Cross-host downloads now run concurrently again (images on one host remain sequential). Follow-up to fully async SSH tracked in #198.
- **FreeBSD image checksum auto-discovery** — checksum probing now recognises FreeBSD's BSD-format `CHECKSUM.SHA512`/`CHECKSUM.SHA256` files (published in the VM image directory), so FreeBSD cloud images get their `sha2`/`sha2_url` resolved and verified automatically instead of logging "Could not find a SHASUMS file".
- **OS image checksum discovery hardened** — checksum (`SHASUMS`) fetching now sends a `User-Agent` header (some CDNs, e.g. CloudFront in front of `cloud.centos.org`, return 403 without one), enforces connect/request timeouts and a 1 MiB download cap, probes additional file conventions (`CHECKSUM`, `.SHA256SUM`/`.SHA512SUM`, Rocky's `.CHECKSUM`), parses digest-only sidecar files (e.g. Alpine's `.sha512`), handles filenames containing parentheses in BSD-format lines, and logs (instead of silently ignoring) transient errors while probing. Affects checksum auto-discovery used by admin VM OS image management.
- **Clean up orphaned custom templates** — a startup data migration now deletes `vm_custom_template` rows not referenced by any VM. Custom templates are 1:1 with their VM, but historical hard-deletes could leave orphans behind. The migration is idempotent (a no-op once clean).

- **Purge historical never-paid soft-deleted VMs** — a startup data migration now hard-deletes VMs that were soft-deleted (`deleted = 1`) while their subscription was never paid (`is_setup = 0`), along with their `vm_history`, `vm_firewall_rule`, `vm_ip_assignment` and orphaned subscription. Never-paid VMs are purged going forward by the worker, but the worker skips already soft-deleted rows so older ones lingered. Ever-paid VMs are left untouched to preserve payment history. Idempotent (a no-op once clean).

- **Data migrations now log their progress** — each startup data migration logs when it starts and a summary of what it did (e.g. "purged 3 of 3 never-paid soft-deleted VM(s)"), so no-op runs are no longer silent.

- **Cascade-delete owned child tables** — added `ON DELETE CASCADE` to pure owned-child tables (SSH keys, passkeys, saved payment methods, referrals/payouts, cached router tunnel/BGP inventory, custom pricing disks). Fixes latent FK-violation failures when deleting a router with cached inventory or a referral with payouts, and simplifies user purges.

### Added

- **On-chain Bitcoin payments** (issue #109) — VMs and subscriptions can now be paid on-chain. A new `onchain` payment method is accepted wherever a payment method is selected (e.g. `GET /api/v1/vm/{id}/renew?method=onchain`); the payment's `data` field returns `{ "onchain": { "address": "bc1…" } }` with a freshly derived receive address (BTC only). The txid is recorded on the payment (`external_id`) once the deposit confirms. Deposits are never rejected: the exchange rate is re-calculated when the transaction is discovered, and the time credited is pro-rated by the value received at that rate (partial, late and over-payments included). Any further deposit to an already-settled address automatically creates a new pro-rated renewal payment. Admin payment-method configs accept a new `onchain` provider type (reuses the LND wallet of the Lightning backend).

- **Transfer a VM to another user (admin)** — new `POST /api/admin/v1/vms/{id}/transfer` (`virtual_machines::update`) reassigns a VM to another user account, e.g. for account recovery (issue #178). It atomically moves the VM and its billing subscription to the target `user_id` and clears the old owner's SSH key from the VM. The change is recorded in VM history as a new `transferred` action. Rejects deleted VMs, self-transfers (`409`) and unknown target users (`404`). Body: `{ user_id, reason? }`.

- **Change OS during re-install** — `PATCH /api/v1/vm/{id}/re-install` now accepts an optional `{ image_id }` body to switch the VM to a different OS image as part of the re-install (issue #177). When omitted, the VM is reinstalled with its current image (unchanged behaviour). The chosen image must exist and be enabled, and the change is recorded in VM history.

- **OS image popularity** — `GET /api/v1/image` now returns a `popularity` field for each OS image: the fraction (0.0–1.0) of active VMs currently using that image (issue #70).

- **Delete (purge) a user (admin)** — new `DELETE /api/admin/v1/users/{id}` (`users::delete`) permanently removes a user and all of their associated data (soft-deleted VMs and their history/IP/firewall rows and 1:1 custom templates, SSH keys, subscriptions and payments, referral records, Nostr domains, passkeys and saved payment methods) in a single transaction. Rejected if the user still has any live (non-deleted) VMs — those must be deleted first so hypervisor resources are released. Admins cannot delete their own account.

- **Manage user passkeys (admin)** — new admin endpoints to view and revoke a user's WebAuthn passkeys.
  - `GET /api/admin/v1/users/{id}/passkeys` (`users::view`) lists a user's registered passkeys (id, optional device `name`, hex `cred_id`, `created`, `last_used`). Credential material is never exposed.
  - `DELETE /api/admin/v1/users/{id}/passkeys/{passkey_id}` (`users::update`) revokes a single passkey. Returns `404` if the passkey doesn't belong to the user, and refuses (`400`) to remove the **last** passkey of a passwordless (`webauthn`) account to avoid locking the user out.
  - `GET /api/admin/v1/users/{id}` now also returns `account_type` (`nostr` | `oauth` | `webauthn`) and `passkey_count`.

- **Permanently delete VMs (admin)** — `DELETE /api/admin/v1/vms/{id}` now accepts an optional `purge` flag in the request body (issue #168).
  - VMs that have **never been paid** (their subscription was never set up) are now **hard-deleted** from the database instead of being soft-deleted, both when an admin deletes them and when the worker's hourly cleanup removes unpaid VMs. Nothing is left behind: the VM row and all related records (history, firewall rules, IP assignments, and the VM's own subscription + line items + payment history) are removed.
  - `purge: true` lets a **super_admin** permanently delete *any* VM — including VMs with payment history — clearing up all related entities. This is intended for removing test VMs. The flag is rejected with `403` for non-super-admins (checked before the VM lookup); regular deletes and never-paid purges are unaffected.

- **Import existing host VMs (admin)** — new admin endpoints to adopt VMs that exist on a host but aren't tracked in the database (issue #166).
  - `GET /api/admin/v1/hosts/{id}/vms/unmanaged` lists VMs present on the host with no matching database record (returns host vmid, mapped database id, name, CPU/memory/disk specs, storage, MAC, running state). The admin service dispatches a discovery job to the worker and reads the reply over a temporary Redis pub/sub channel.
  - `POST /api/admin/v1/hosts/{id}/vms/import` (`{ host_vm_id, user_id, reason? }`) imports one VM: it is assigned to `user_id` and billed via the region's **custom pricing** (required — import fails if the region has none), capturing the VM's current CPU/memory/disk specs into a custom template. Currently supports Proxmox hosts. Returns a `job_id`.

- **Per-request OAuth return URL** — `GET /api/v1/oauth/{provider}/login` now accepts an optional `?redirect=<url>` to override the configured `success-redirect` for that login only (e.g. `http://localhost:3000/oauth/complete` in dev). The URL is validated against a new `allowed-redirects` allowlist (`localhost` host always allowed; `success-redirect` always implicitly allowed) and rejected with `400` otherwise, then round-tripped through the signed `state`. See the OAuth login flow in API_DOCUMENTATION.md for details and a `config.yaml` example.

  - New `fetch`-based endpoints `POST /api/v1/webauthn/register/start` + `/register/finish` (creates a passwordless account) and `POST /api/v1/webauthn/login/start` + `/login/finish` (usernameless / discoverable login). Each `start` returns a `challenge` for the browser `navigator.credentials` API plus an opaque signed `state`; the matching `finish` posts back that `state` with the credential and returns a `{ token, token_type, expires_in }` session response.
  - Uses the same stateless session **JWT** as OAuth (`Authorization: Bearer <jwt>`), so passkey users reach every existing authenticated endpoint. Configured under a new `webauthn` config section (`rp-id`, `rp-origin`, `rp-name`); the signing secret lives in the shared `session` block (below).
  - Passkey accounts are stored with a new `account_type` of `webauthn` and a synthetic identity (`sha256("webauthn\\0{user_handle}")`, in a namespace provably disjoint from OAuth). Like OAuth accounts they have no usable Nostr key: NIP-17 DMs, npub display and LIR signing are gated off, and `GET /api/v1/account` reports `account_type: "webauthn"`. Credentials are stored in the new `user_webauthn_credentials` table (one account may register several devices).
  - **Add passkeys to existing accounts:** authenticated endpoints `GET /api/v1/webauthn/credentials` (list), `POST /api/v1/webauthn/credentials/start` + `/finish` (register another passkey to the current account — any account type, Nostr/OAuth/passkey), and `DELETE /api/v1/webauthn/credentials/{id}` (remove one). A later discoverable login with such a passkey resolves back to the same account (by credential id), so its session token carries the account's real identity. A pure passkey account cannot delete its only credential.

- **2026-07-18** - Generic OAuth / OIDC login (Google, GitHub, Facebook, Apple)
  - New endpoints `GET /api/v1/oauth/{provider}/login` (redirects to the provider) and `GET`/`POST /api/v1/oauth/{provider}/callback` (exchanges the authorization code, resolves/creates the user and issues a session token). Providers are configured under the new `oauth` config section, each with a `type` of `google`, `github`, `facebook`, `apple`, or generic `oidc`.
  - Built-in flavors handle each provider's quirks: GitHub's `User-Agent` requirement and numeric `id` subject, Facebook's Graph `me` endpoint, and Sign in with Apple's `id_token`-based subject, dynamically-signed **ES256** client secret, and `form_post` (POST) callback.
  - After a successful login the API issues a stateless session **JWT**. It is accepted on every existing authenticated endpoint via `Authorization: Bearer <jwt>`, alongside the existing `Authorization: Nostr <event>` (NIP-98) scheme. The JWT signing secret and lifetime live in a shared top-level `session` config block (`session.secret`, `session.ttl`) used by both OAuth and WebAuthn — required whenever either login method is enabled.
  - On first login the provider's email is synced into the account (marked verified when the provider asserts it) and email notifications are enabled by default, since OAuth accounts have no NIP-17 channel. GitHub's primary verified address is fetched from `/user/emails`; Apple's email comes from the `id_token`. The sync is non-destructive — a user's later email edits are not overwritten — and best-effort (a sync failure never blocks login).
  - OAuth accounts are stored with a new `account_type` of `oauth` and a synthetic identity (`sha256("{provider}:{subject}")`) in place of a Nostr pubkey. Nostr-only features (NIP-17 DMs, npub display, LIR agreement signing) are gated to native Nostr accounts.
  - `GET /api/v1/account` now returns `account_type` (`nostr` | `oauth`, read-only) so the frontend can hide Nostr-only UI for OAuth users. `PATCH /api/v1/account` rejects enabling `contact_nip17` for OAuth accounts (their pubkey is not a usable Nostr key).

### Fixed

- **Passkey usernameless login failing on non-synced authenticators** — passkey registration now always creates a **discoverable (resident-key)** credential (`residentKey: "required"`, `userVerification: "required"`), so "Sign in with a passkey" reliably works on security keys and Windows Hello, not just synced platform passkeys (iCloud Keychain / Google Password Manager). - **2026-07-16** - VAT is now charged using EU place-of-supply rules instead of a flat per-country lookup
  - **EU VAT only, gated on the seller.** The seller's country is taken from the company's own VAT number (`tax_id`, i.e. its VIES registration) when set, else `country_code`. Tax is applied only when that country is in the EU VAT area. A non-EU seller (e.g. a US company) charges no tax here; other systems such as US sales tax are not handled.
  - When the seller is in the EU, the tax charged is determined from the **seller's country** and the **customer's status/location**:
    - **B2B** with a stored (VIES-validated) VAT number: same country as seller → domestic VAT; another EU country → **reverse charge** (0%); outside the EU → out of scope (0%).
    - **B2C**: place of supply is taken from the self-declared country, falling back to the IP-derived country. EU → that country's destination rate (OSS); non-EU → out of scope (0%).
    - **Undetermined** (no customer country evidence): the seller-country rate is applied as a fallback.
  - **Behaviour change:** non-EU customers are now correctly out of scope (0%). Previously any country present in the `tax_rate` config map was charged its configured rate regardless of EU membership (e.g. a placeholder `USA: 1%`).
  - **Config removed:** the static `tax-rate` config map is gone. Standard EU rates for all member states are now fetched at startup and refreshed daily, cached in-memory by a shared cloneable `VatClient` (formerly `EuVatClient`). Until the first successful refresh, VAT falls back to 0%.
  - New public API in `lnvps_api_common`: `PricingEngine::determine_tax` (full treatment + audit detail), `TaxTreatment`, `TaxDetermination`, `is_eu_vat_country`, `vat_number_country_alpha3`; `VatClient` gains `refresh_rates`/`rate_for`/`with_rates`. `get_tax_for_user` now also takes the seller `company_id`.

Proxmox HTTP errors are now classified fatal/transient by status code instead of blanket-retrying 4xx.
  - **Renewals & pricing:** a pending renewal invoice is no longer reused for a request covering a different number of intervals (which let a multi-interval request be paid off with a smaller single-interval invoice); VPS-only subscription setup fees are now charged on the first invoice; and extending an already-expired VM now clamps the new expiry to "now" consistently with every other renewal path.
  - **Robustness:** fixed remote-triggerable panics in NIP-98 auth (malformed single-element tags) and VAT-number parsing (multi-byte input), and a panic in VM status when an IP range fails to load.
  - **Admin/DB:** creating or updating available IP space now persists `company_id` (the insert previously failed on the NOT-NULL column); non-VM subscription payments are correctly attributed to their company in admin payment views and revenue reports; `admin_update_company` now persists `base_currency`; and per-region capacity stats no longer under-count hosts that share the same CPU/memory values.
  - **Support agent, health checks & host tooling:** the support agent no longer crashes on non-ASCII messages or empty LLM responses, uses UID-based IMAP operations (no duplicate replies), and URL-encodes email lookups; health-check metrics handle IPv6 DNS servers and IPv6 bind addresses; and host CPU-feature detection uses a safe CPUID intrinsic with a max-leaf guard.
  - **XDP firewall:** corrected the SYN rate-limiter token-bucket refill math (previously refilled far too fast, defeating the limit), stopped counting SYN-ACK replies, and guarded against a zero-limit division.

- **2026-06-25** - Admin VM `template_id` is now `null` for custom-template VMs
  - `AdminVmInfo.template_id` (returned by `GET /api/admin/v1/vms` and `GET /api/admin/v1/vms/{id}`) changed from `u64` to a nullable integer. VMs on a custom template previously reported `template_id: 0`; they now correctly report `template_id: null` (with the linked template carried by `custom_template_id`). Standard-template VMs are unaffected.

- **2026-06-25** - Expired subscriptions are now handled even when expiry predates the last check
  - The worker's `CheckSubscriptions` expiry handling previously only fired when a subscription crossed its expiry between two check cycles (`expires >= last_check`). Subscriptions that expired before the last check (admin/retroactive expiry, clock changes, or worker downtime) were left running until the grace period elapsed. The worker now fires the one-shot expiry handling (stop VM + notify) for any expired-but-in-grace subscription, using VM history as an idempotency marker so it still acts exactly once.

- **2026-06-23** - Toggling a BGP session now persists on routers where the backend session id differs from the session name (e.g. Mikrotik, where the id is `.id` and the name is the protocol name). Previously `POST /api/admin/v1/routers/{id}/bgp/sessions/toggle` updated nothing in the cache for such routers because the persist was keyed by the backend id instead of the cached session name.

- **2026-06-16** - VM→subscription backfill now runs reliably at startup
  - The backfill is executed during app startup, after schema migrations and before any VM read, and preserves each VM's existing expiry and auto-renewal preference. The legacy `vm.expires` / `vm.created` columns are no longer dropped before the backfill runs, which previously caused the backfill to fail for every VM and break all VM reads. (No external API surface change — listed for operator awareness.)

- **2026-04-26** - Region capacity no longer reports IP ranges as full incorrectly
  - `GET /api/v1/vm/templates` and region availability — the gateway IP is now only counted as a used address when it actually falls within the allocation CIDR. Previously a gateway outside the range inflated the used-IP count and could falsely report a region/range as full while free IPs remained.

- **2026-04-02** - Payments for already-deleted VMs are handled gracefully
  - `POST /api/v1/vm/{id}/renew` and payment confirmation — a payment that arrives for a VM auto-deleted before the (slow) payment settled now un-deletes the VM and applies the payment instead of erroring; the VM is then re-provisioned by the next check. Renewal/invoice creation for VMs that remain deleted is rejected with `"VM not found"`.
  - A race where a VM paid between the cleanup snapshot and the deletion step could be deleted is fixed by re-reading VM state immediately before deletion.
